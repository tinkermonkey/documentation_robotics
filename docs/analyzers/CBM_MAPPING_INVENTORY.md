# CBM mapping inventory (2026-10-28, updated for CBM 0.12.1 on 2026-11-05)

Phase 2 of [EXTRACTION_STRATEGY.md](../EXTRACTION_STRATEGY.md) widens `spec/analyzers/cbm` to the rest of codebase-memory-mcp's (CBM) vocabulary. This document is the starting inventory: every CBM node label and edge type, what `spec/analyzers/cbm/*.json` says about it today, and, for the unmapped ones, the candidate Documentation Robotics (DR) type or predicate checked against the relationship catalog in `spec/dist/*.json`. It changes nothing; it is the list the mapping work is scoped from.

**Progress (2026-10-29):** steps 1 to 4 of the widening order below are applied on the
`feature/phase2-cascade` branch, with two departures from the plan. `HTTP_CALLS` was downgraded to
traversal-only rather than kept with a note, so no relationship-creating edge names a missing
triple. The `Interface` fallback narrows to the application layer only (data object, application
interface, application event), not to data-model as well: Clef put 35 of dr-cli's 60 interfaces in
data-model when it was offered, against a charter-labelled gold that files in-code interfaces as
application data objects. Steps 2 and 4 are Tier-0 rules in `extraction-heuristics.json`, measured
in the Phase 2 results of [EXTRACTION_STRATEGY.md](../EXTRACTION_STRATEGY.md).
`cli/tests/unit/analyzers/cbm-mapping-catalog.test.ts` keeps the mapping consistent with the
catalog from now on.

Later the same day steps 5 to 7 landed too, and every one of the 48 edge types is now in
`edge-mapping.json`: 17 create relationships through a per-pair catalog lookup over an ordered list
of predicates (`cli/src/analyzers/edge-relationships.ts`), and the other 31 say why they do not.
(Corrected 2026-11-12: the mapping now lists 48 edge types, 17 of which create relationships; the
0.12.1 update below dropped three edges, `HTTP_CALLS` and `INHERITS` were mapped since, `READS`,
`SUPERSEDES` and `DIAGRAM_ARROW` were added as traversal-only, and `ASYNC_CALLS` and `LISTENS_ON`
became traversal-only because neither end they need is ever an element.)
Of the ten catalog additions below, eight (eleven triples) are proposed to Context Studio as create
operations (`cli/scripts/spec-enrich/data/catalog-additions-cbm.json`); addition 6 duplicates
`application.applicationservice serves application.applicationcomponent`, and additions 8 and 10
duplicate the reversed triples `SPAWNS` and `DEPLOYS` now use. The compose `depends_on` half of
addition 9 is proposed as `technology.node depends-on technology.node`, not `composes`.

On 2026-11-03, after an independent review, the maintainer settled two modelling points this
inventory had left implicit: a route handler is the application function its Route's operation
realizes (as the `HANDLES` row says), not a second operation, and an ORM table class is a data-model
object schema whatever the framework, with its table a derived data-store collection. Edge
mappings now also carry enforced end-type restrictions (`conditions.from_types` / `to_types`).

### Findings

1. **The discover-side test filter missed most test code; `is_test` is not the fix.** `extraction-heuristics.json`'s `test_code_exclusion` pattern, `^.*(\.test\.|_test\.|spec\.|__tests__)`, matched none of petclinic's 20 test files (`src/test/java/**/*Tests.java`) and 6 of fastapi's 22 (it missed `tests/test_*.py`). CBM's `is_test` (a string, `"true"`) flags all of them, but measured symbol by symbol against the broader pattern the `tier0_test_file` rule already used, it adds only false positives (dr-cli's `src/audit/*/spec/` sources, fastapi's `packages/react-email/emails/test_email.tsx` email template) and misses 23 petclinic symbols in `src/test/java`. The test pass (2026-11-05) therefore makes that pattern, extended to `fixtures/` directories and `conftest.py`, the one definition of test code for both the Tier-0 rules and `test_code_exclusion`. This settles the "Java `test_code_exclusion`" item.
2. **`HTTP_CALLS` comes from tests.** CBM marks 53 of fastapi's 55 callers and 81 of dr-cli's 86 as test code. The catalog already has `testing.testcasesketch tests api.operation`, so the test pass (step 7) can map these with no catalog addition. Catalog addition 7 (application code consuming an operation) is still the route for production callers, which are rare here (dr-cli's `src/core/model.ts`, 4).
3. **Routes still need the filter.** 65 of dr-cli's 73 `Route` nodes are `ANY` "routes" built from file paths and model paths (`/project/src/service.ts`, `/documentation-robotics/model`), as on 0.10.2, so `isLikelyHttpRoute` stays. New: `external: "true"` marks routes on other hosts (a GitHub release download, `localhost:8000` health checks), which are not this system's operations, and `source: "decorator"` marks petclinic's 15 annotation-declared routes. Excluding `external` routes is a one-line rule. (Done 2026-11-12: `codebase_verify` and `dr analyzer endpoints` drop `external` routes, routes with `source: "openapi"` (a route only an OpenAPI file declares), and routes with neither a file nor a handler, which is the extraction rule.)
4. **`RAISES` is mostly noise.** 77 of dr-cli's 160 point at a rethrown `error` variable; the rest at error classes (`CLIError` 68, `ModelNotFoundError` 7). Keep it traversal-only. Error classes are evidence at most.
5. **The 11 CBM catalog additions are reviewed (#1004, 2026-11-06).** 8 landed, 3 of them reversed into `serves` (`api.operation serves applicationfunction` and `applicationcomponent`, `technologyservice serves node`); `applicationcomponent triggers applicationevent` and `applicationinterface depends-on applicationevent` were rejected by the application rules; `applicationfunction triggers applicationevent` was already added in #1002. The edges they unblock are not mapped yet: interface-level `LISTENS_ON` and component-level `EMITS` stay unmapped, and `EMITS` maps at function level only.

### Documentation evidence (2026-11-12, #1085)

`codebase_extract` now reads CBM's documentation graph. Nothing in it is mapped to a DR type: `ADR`
and `Section` stay in `unmapped_labels`, and `SUPERSEDES`, `MENTIONS` and `REFERENCES_FILE` stay
traversal-only. They are evidence the calling agent (Tier 2) works from
(`cli/src/analyzers/cards/docs.ts`, `cli/src/analyzers/decision-records.ts`).

No eval corpus has a decision record, so the shapes below come from a fixture,
`cli/tests/fixtures/cbm-docs-repo/`: four Nygard-style records in `docs/adr/` (2 superseded by 3, 4
only proposed), a README whose sections name the code, and two TypeScript files. Its CBM 0.12.1
responses are recorded in `cli/tests/fixtures/cbm-0.12.1/cbm-docs-repo.responses.json`, with the
script that re-records them beside it.

- **`ADR` nodes.** One per record file, named `ADR-<n>` (qualified name `<file stem>.__adr__`), with
  `adr_id`, `title`, `status` (lower-case: `accepted`, `proposed`, `superseded`), `status_text` (the
  status line as written), `date`, `deciders` and `superseded_by` (the newer record's file name, as
  linked). The decision text is in `docstring`; there is no `decision` property. Context and
  consequences are only in the record's `Section` nodes.
- **`SUPERSEDES`** runs from the newer record to the older (`ADR-3 → ADR-2`), from a "Supersedes
  [2. ...](0002-...md)" line (`syntax: supersedes`, `tier: exact`, `via: markdown`). The older
  record's "Superseded by" line sets its `status` and `superseded_by` but makes no edge of its own.
- **`Section` nodes** are headings with their text in `docstring` (lines in `start_line` /
  `end_line`). dr-cli has 647.
- **`MENTIONS`** runs from a section to a symbol named in backticks with its owner
  (`OrderService.placeOrder`, `syntax: code_name`), or to a `File` or `Folder` it links or names as
  a path (`syntax: link` / `code_path`). A bare class name (`OrderStore`) made no edge. On dr-cli,
  all 64 mentions are files and folders.
- **`REFERENCES_FILE`** runs from a doc `File` to a code `File` (`strategy: md_inline_link`,
  `md_backtick_path`, `md_bare_mention`), with no section. On dr-cli most come from `CHANGELOG.md`.
- **`get_code_snippet`'s `possibly_described_in`** lists sections by shared terms, not links, with
  a probability (`p: 0.22` for the fixture's README title on `placeOrder`). Extraction reads source
  from disk and makes no snippet call per card, so it isn't used; it would cost one call per card.

How extraction uses them:

- **Decision records → motivation.** An active record (not superseded, deprecated or rejected, and
  superseded by no other record) with no element yet becomes a `decision-record` card: candidates
  `motivation.principle`, `constraint` and `assessment`, symbol `ADR-<n>`, file the record, and a
  `decision` block (id, title, status, date, deciders, decision, context, consequences, the records
  it supersedes, and up to 8 files or symbols its sections mention). The agent proposes the type
  and name and stages it with the record as its source reference, or rejects it. A record any live
  element names (by file) is counted as modelled. A retired record gets no card and is listed under
  `documentation.decisionRecords.retired` (a record superseded only by a record that is itself only
  proposed is still active); an element every location of which is a retired record is a candidate
  delete (`evidence: "decision-superseded"`). Records under test, fixture and vendored paths are
  left out (DR's own index holds the fixture's four). With `since`, only records whose file the
  range changed count (the range's scope keeps decision-record files even when no element names
  them), and a retired record also when a record that supersedes it changed; only those retired
  records are listed.
- **Doc sections → descriptions.** Each card carries up to 2 `docs` entries (doc file, section,
  lines, a 240-character excerpt, and `via`): sections that mention the symbol first, then, for a
  module or a top-level declaration (not a method or route), sections or doc files that name its
  file. Changelogs and decision records are left out. Staged adds with no description that a doc
  section describes are listed under `documentation.describe` (at most 10, one excerpt each), for
  the agent to write their descriptions. The response shortens excerpts to 100 characters, then
  drops them, to stay under its budget.
- **Semantic search (`search_graph` with `semantic_query`)** is not used: no existing DR tool has a
  natural place for a free-text query. It is a candidate for orientation while planning (finding
  the code behind a goal or requirement), as an optional query on a planning tool.

### Infrastructure mapping (step 9, 2026-11-12, #1081)

**What is mapped.** `node-mapping.json` maps:

- `Table` → `data-store.collection` (collectionType `TABLE`);
- `Image` and `Chart` → `technology.artifact` (an image's artifactType is `container-image`);
- `Resource` → `technology.node`, as a hint only;
- `Process` → `technology.systemsoftware`.

`Table`, `Image` and `Chart` are decided by label. Tier-0 rules in `extraction-heuristics.json` decide `Resource` by the kind CBM puts before the slash in its name:

- a compose service → `technology.node` (`tier0_compose_service`, keyed on the compose file name);
- a Deployment, StatefulSet or DaemonSet → `technology.node`;
- a Kubernetes Service → `technology.technologyservice`;
- a Secret → `technology.artifact` with artifactType `configuration`: configuration deployed with the workloads that read it. A secure resource it guards is modelled from intent, not from the manifest.

Other kinds (ConfigMap, Ingress, Job, ...) go to the agent. A Tier-0 rule decides `Process`, and `<dynamic>` (a program named at run time) is no element.

**Extraction changes.**

- **Merging by name.** A name declared in several files is one element with every file as a source location: a table in each dialect's `schema.sql`, a compose service in each compose file.
- **Names.** search_graph gives an infrastructure node's name as the tail of its qualified name (`yml::apps/Deployment/-/demo-db`, or `com/vscode/devcontainers/java` for an image whose name has dots). The card builder reads the stored names back with one query per label.
- **Merge key.** The merge key is the decided type, the label and the name, so a compose service and a Kubernetes Service of one name (`Service/db`: a node and a technology service) stay two elements.
- **Files.** A `since` extraction keeps SQL, Dockerfile, compose, Kubernetes and Helm changes in scope (`Chart.yaml`, YAML under `k8s/`, `helm/`, `charts/`, `deploy/` and the like), not every YAML file: lockfiles and CI workflows stay out. Images and launched programs have no file, so only a full extraction picks them up.
- **Required attributes.** A technology service's serviceType, system software's softwareType and a chart's artifactType are not in the graph. Those adds come back as needs-attributes cards.

**Edges.** `INFRA_MAPS` (workload realizes service) and `DEPENDS_ON` (compose `depends_on`, `technology.node depends-on technology.node`, now in the catalog) create relationships. So does `USAGE` from a workload or compose service to the image it runs (`ref: image`): `technology.node composes technology.artifact`, a scoped-pair preference in the `USAGE` mapping that sits beside its data-object targets without widening them (#1107 follow-up). `SPAWNS` does only from an application component: the catalog has no triple from an application function to system software, and a Dockerfile is a `Module` with no card. `DEPLOYS` still creates none on the corpora: its deployer is a CI workflow and what it deploys is a `File`.

**Measured** (`cli/scripts/classify-eval/infra-report.ts`, gold hand-labelled before the run in `data/<corpus>/infra-gold.json`, reports `data/infra-report@before.md` and `@after.md`). ## Smaller opportunities (#1086, 2026-11-12)

Measured on CBM 0.12.1 against the three eval-corpus indexes (dr-cli rebuilt from `cli/` at `450e650f`, the commit its cards come from) and an index of heimdall. Federation, architecture clusters and runtime traces are deferred.

### Call-edge evidence

CBM stores how it resolved each `CALLS` edge on the edge itself: `{"callee":"radiusOf","strategy":"suffix_match","confidence":0.28,"candidates":3,"line":47}`. Functions, methods and classes carry `importance` (weighted degree); fields and variables carry none. `trace_path` with `include_evidence` returns the same confidence per hop, but coarsens the strategy to `lsp` or `heuristic`, needs one call per function, and leaves out some edges (it omitted heimdall's `packClusters` → `laneLayout.test.layout`). The bulk Cypher read extraction already makes returns the edge properties and the callee's importance (`r.strategy, r.confidence, r.candidates, r.callee, b.importance`), so the gate costs no `trace_path` calls and one extra `query_graph` per run (the project's `IMPORTS` edges with their `local_name`).

Strategies and confidences seen: LSP and import-map resolutions at 0.85 to 0.97, `same_module` 0.9, `unique_name` 0.75 or 0.38 (one candidate), `suffix_match` 0.55 (two candidates) down to 0.04 (23 candidates). Below 0.5 is 3 to 26% of a graph's calls: dr-cli 200 of 4,224, petclinic 92 of 357, heimdall 332 of 2,653, fastapi 20 of 644.

Hand-checked sample (`cli/scripts/classify-eval/data/call-edges-truth.jsonl`, `bun call-gate-report.ts`): up to 8 edges per strategy and confidence band per index, each judged from the call line and the caller file's imports. Agent-labelled, not reviewed by the maintainer.

| sample   | band             | edges | real      | gate keeps (real / wrong) | gate drops (real / wrong) |
| -------- | ---------------- | ----- | --------- | ------------------------- | ------------------------- |
| design   | confidence ≥ 0.5 | 218   | 211 (97%) | 211 / 7                   | 0 / 0                     |
| design   | confidence < 0.5 | 53    | 20 (38%)  | 16 / 0                    | 4 / 33                    |
| held-out | confidence < 0.5 | 36    | 18 (50%)  | 10 / 0                    | 8 / 18                    |

The wrong low-confidence edges are names matched to the wrong definition: a callback parameter (`fn`, `radiusOf`, `onSelect`, `querySerializer`), a library function with a project namesake (tests' `writeFile` from `fs/promises`, yaml's `parse`, React's `useState` matched to a design-reference prototype), a field (`view().name` on `NamedEntity.name`, 15 candidates). The right ones are member calls on a receiver with a unique name (petclinic's tests, fastapi's `crud.*`), `this.m()` in the same file, and bare calls the file imports, statically or through a directory index. The gate (`call_edge_evidence` in `extraction-heuristics.json`, run by `cli/src/analyzers/call-evidence.ts`) keeps every edge at confidence 0.5 or more, and a lower one only on one of those three corroborations, never when the callee has no importance. On the held-out sample, drawn and labelled before the gate ran on it, it dropped all 18 wrong edges and 8 of 18 right ones (the `own-member` rule was added after seeing two of those 18). The right edges it drops are dynamic imports (`await import(...)`, which CBM records no `IMPORTS` edge for) and suffix matches on a receiver. The 7 wrong edges above 0.5 are out of its reach: `import_map` binds `it` / `describe` / `test` to `bunfig.toml` or to a project method named `test` (an upstream bug, #1087), and a `MutableConfiguration` constructor to `pom.xml`. On whole graphs the gate drops 3.6% of dr-cli's calls, 0.5% of fastapi's, 11.8% of petclinic's (mostly `view().name`) and 11.5% of heimdall's.

Importance as a magnitude does not separate right from wrong: wrong targets collect spurious callers (`writeFile` 84.9, heimdall's `onSelect` 85.4), right ones span 0.1 to 77. Only its absence is a signal.

The edge report (`edges-report.ts`, gold node labels standing in for edge gold) cannot see the gate: none of the 80 call edges between its sampled production cards is below 0.5 without corroboration, so precision and recall are the same with and without it, 51% and 47% (81 gold-typed relationships, 74 produced, 38 identical). The #1001 baseline of 42% and 38% predates the `INHERITS` → `specializes` mapping (+11 produced, all agreeing) and the catalog changes since; the report is regenerated in `data/edges-report.md`.

### The false `depends-on` on heimdall (#1095)

`application.applicationfunction.cluster-circle-packing depends-on application.applicationfunction.galaxy-radial-orbit-layout-algorithm` comes from one CBM edge, `CALLS` from `src/utils/graphPacking.ts::packClusters` to `src/utils/galaxyLayout.ts::radiusOf` (line 47, `radiusOf(node.data.id)`), with `strategy: suffix_match`, `confidence: 0.28`, `candidates: 3`. `radiusOf` is a callback destructured from `packClusters`'s options; heimdall defines three functions of that name (`galaxyLayout.ts`, `graphLayout.ts`, a spec file), and CBM picked one. `radiusOf` has no element of its own, so extraction rolled it up to the galaxy layout element. A `USAGE` edge from the `graphPacking` module to the same `radiusOf` exists too; `USAGE` carries no resolution evidence, so the gate does not cover it, and it creates a relationship only when the module itself is an element. The gate drops the `CALLS` edge (`uncorroborated`: `graphPacking.ts` imports only `d3-hierarchy` and `./graphClustering.ts`), checked end to end through the extraction read on the round-3 index. The same function's other call edge, `layout(...)` matched to a test's local `layout` (`unique_name`, 0.38), is dropped too (`not-callable`). Remembering rejected relationships (the rest of #1095) is separate work.

### `OTEL_*` environment variables

`EnvVar` nodes now become cards when a deployment file declares them (compose, Kubernetes, Dockerfile); one the code only reads (`__env__KEY`, no file) does not, since the code reading it is the candidate and its card lists the variable. Two Tier-0 rules decide them: `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_{TRACES,METRICS,LOGS}_ENDPOINT`, `OTEL_EXPORTER_JAEGER_ENDPOINT` and `OTEL_EXPORTER_ZIPKIN_ENDPOINT` are `apm.exporterconfig` (the type's own evidence names these keys); every other variable is no element. Only the endpoint key becomes an element, because the protocol, headers and compression keys configure the same exporter. The element is named after its container (`apm.exporterconfig.backend-otel-exporter-otlp-endpoint`), with `type` from the key, `endpoint` from the declaring line, and `protocol` and `compression` from the same container's protocol and compression keys (the signal's own, else the exporter's); a Kubernetes entry keeps its value on the next line, so it comes to the agent as a needs-attributes card. None of the four indexes declares an `OTEL_*` variable in a deployment file (dr-cli reads three in code), so this is covered by tests only. Not mapped: `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES` (`apm.resource`) and the sampler keys (`apm.traceconfiguration`), which describe other types and were not asked for.

## Architecture clusters (2026-11-12, #1086)

`get_architecture` is not part of the label and edge vocabulary, but it is CBM's other answer to
"which symbols belong together". Inspected on CBM 0.12.1 against dr-cli (the eval checkout at
`450e650f`, and `cli/` on `main`), fastapi and petclinic:

- **`aspects: ["system_structure"]`** must be asked alone and with no `path`. The first call
  answers `{status: "pending", generation, retry_after_ms: 500}`; a later call in the same server
  session answers `{status: "ready", result}` (0.7 s on petclinic, 1.3 s on fastapi, about 10 s on
  dr-cli). A one-shot `codebase-memory-mcp cli` call never gets past `pending`, because the process
  exits with its job. The result is a list of component candidates: one per declared module (a
  file or class), `unassigned` nodes, and `interaction_community` components that merge several
  files whose symbols call and use each other. dr-cli at `450e650f` has 1,021 (256 shown, the rest
  only counted), fastapi 331 (256 shown) and petclinic 252 (167 declared modules, 78 unassigned, 7
  communities). A component lists one representative and counts the rest (`omitted_members`); other
  members are named only as dependency witnesses, entrypoints and path nodes, which places 1,000 of
  dr-cli's 7,511 nodes, 649 of fastapi's 1,744 and 445 of petclinic's 1,376. No node property
  records the component, so `query_graph` can't list membership either.
- **`aspects: ["clusters"]`** is Louvain over `CALLS` edges only: at most 12 communities, each with
  a member count, cohesion and its five top symbols by bare name (no qualified names, no ids). The
  communities cover 1,030 of dr-cli's 7,511 nodes and mix test code with what it tests.

A declared-module component says no more than the card's own file does, so only cross-file
components are evidence. `codebase_extract` with `clusters: true` attaches them (`cluster` on a card)
and offers the largest non-test interaction communities as component proposals; Tier-0 decisions are
not touched. It is off by default because the evidence did not improve component assignment on the
gold sets: see "Architecture clusters" in [EXTRACTION_STRATEGY.md](../EXTRACTION_STRATEGY.md).
`get_architecture` is in the analyzer's `optional_tools`.

## Cross-repository edges (federation, 2026-11-12)

Issue #1086 asked whether CBM's cross-repo-intelligence output maps to DR's cross-model references
(`@{model}/{layer}.{type}.{name}` in an element's `references`). The eval corpora are single
repositories, so the shapes below come from three fixture repositories built for it: a FastAPI
`svc-orders` serving `POST /api/orders` and `GET /api/orders/{order_id}` and producing to a Kafka
topic, a Python `svc-shipping` that calls `GET http://svc-orders:8000/api/orders/{id}` with
`requests`, consumes the topic and emits socket.io events, and a TypeScript `web-client` that
`fetch`es both order routes and listens to a socket.io event. Each was indexed (`mode: "full"`),
then linked with `index_repository mode: "cross-repo-intelligence", target_projects: [...]` on
CBM 0.12.1.

### What CBM writes

| Edge                                                                               | Observed | Shape                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CROSS_HTTP_CALLS`                                                                 | yes      | In the calling project: caller `Function` → the caller's own client `Route` (`__route__GET__http://svc-orders:8000/api/orders/{}`, or `__route__ANY__/api/orders` when the call names no method). Properties: `target_project` (the serving CBM project), `target_function` and `target_file` (the handler there, short name), `url_path`, and `transport` (the HTTP method) only when the caller's code names it. CBM matched an `ANY` call to the right handler by path. |
| `CROSS_HTTP_CALLS` (serving copy)                                                  | yes      | In the serving project: handler → its own Route, with `target_*` naming one caller. One per handler and route: a second caller's run overwrites it (two callers of `get_order`, one copy).                                                                                                                                                                                                                                                                                 |
| `CROSS_CHANNEL`                                                                    | yes      | From the emitting or listening `File` (EMITS and LISTENS_ON have file sources) to the project's own `Channel`, with `target_function` set to the other file's name, `target_file`, `channel_name` and `transport` (`kafka`, `socketio`). Written into both projects; the edge does not say which side emits. A Kafka producer and consumer linked this way, not as `CROSS_ASYNC_CALLS`.                                                                                    |
| `CROSS_ASYNC_CALLS`, `CROSS_GRPC_CALLS`, `CROSS_GRAPHQL_CALLS`, `CROSS_TRPC_CALLS` | no       | The binary's queries read `ASYNC_CALLS` and per-transport call edges, but no fixture produced them (an SQS `send_message` produced no `ASYNC_CALLS` at all).                                                                                                                                                                                                                                                                                                               |

Other facts that shape the design:

- A repository is identified by its CBM project name (derived from the indexed path unless
  `index_repository` is given `name`); `list_projects` gives each name's `root_path`.
  `target_projects` is required (`["*"]` for every indexed project) and every target must be
  indexed already.
- A full re-index of a repository drops its `CROSS_*` edges (observed), so the pass must follow
  every index. It is cheap: 50-300 ms on the fixtures, reading no files.
- The pass replaces the repository's earlier cross-repo edges and writes copies into the targets.

### The mapping

Implemented on 2026-11-12, opt-in (`cli/src/analyzers/cross-model.ts`):

- **Opt-in.** `codebase_index` with `crossRepo: [{codebase, model?, modelPath?}]` records the other
  repositories in `.dr/analyzers/cbm/cross-repo.json`. Without that file nothing changes: no
  extra CBM call when indexing, no extra query when extracting.
- **Repository to model.** Each repository is tied to a model the manifest declares under
  `models:`, by name, or by its `origin` remote matching the declared `url` (normalized, so ssh
  and https forms compare equal). An undeclared model is refused; DR never edits the manifest.
- **Indexing.** Each index run ends with the cross-repo-intelligence pass against the targets'
  CBM projects (found by root path; a repository CBM has not indexed is indexed first, without
  writing a `.cbmignore` into it). The result is kept as `lastRun` and shown by `codebase_index`.
- **Edges.** Only `CROSS_HTTP_CALLS` from the calling side. The serving copy is skipped (a
  reference belongs to the consumer's model), `CROSS_CHANNEL` is counted and left out (a Channel
  is not an element on either side, #1080), and the unobserved kinds are counted and left out.
- **Source.** The caller's element in this model: its own, else the class or module it is in,
  as `planRelationships` rolls a member up. A caller that is only a card gets its reference on the
  run after it is staged. Elements never take a qualified path as their id: the reference sits in
  the caller's `references`, and the target is `@model/<id in that model>`.
- **Target.** The route is read from the target project (`HANDLES` of `target_function` in
  `target_file`, which gives the method an `ANY` call lacks and the code's parameter names). Then
  the target model on disk (the repository, or `modelPath`; read like `--model-path`) is searched
  for the `api.operation` with that method and path, the handler's file breaking a tie, and for
  the handler's element by file and symbol. With no model there, the reference is staged
  **unverified**, to the id extraction would give that route in that repository
  (`api.operation.get-api-orders-order-id`), and its description says so. With a model that has
  no matching element, nothing is staged and the call is listed under `unresolved` with the
  candidate id.
- **Predicate.** The first catalog triple from the caller's type to the operation (`tests`,
  `triggers`, `references`: a test case, a UX action, a route's metadata), else to the handler's
  element (`flows-to`, from application code only, as `DATA_FLOWS`). Nothing is added to the
  catalog. An application caller has no triple to `api.operation` (catalog addition 7), so a
  production caller is referenced only when the other model has the handler as an element.

Checked end to end on the fixtures with CBM 0.12.1 and a DR model in `svc-orders`: the pass ran
for `svc-shipping` and `web-client`, and `codebase_extract` in `svc-shipping` resolved
`fetch_order`'s call to `GET /api/orders/{order_id}` and staged a verified
`application.applicationfunction.fetch-order` **flows-to**
`@svc-orders/application.applicationfunction.get-order` reference. With only the operation in that
model it staged nothing and listed the call as unresolved (no triple from an application function
to `api.operation`). `web-client`'s two callers are undecided cards, so they were counted and
left for a later run.

Open: the predicates for `CROSS_CHANNEL` wait on channels becoming application events (#1080);
the unobserved kinds wait on a repository that produces them; a target repository's index is not
refreshed when it is stale, only when CBM has none.

## Summary

- CBM documents 28 node labels; the mapping names 12 (5 mapped, 7 listed as unmapped). 16 labels are absent from the mapping altogether, including `Variable` (the most numerous node in every corpus), `Decorator`, `Field`, `Section`, `Channel`, `EnvVar`, `Table` and every infrastructure label.
- CBM documents 42 edge types (plus 6 seen only in the binary or UI). The mapping names 13. Of those, five (`CREATES`, `USES`, `REFERENCES`, `RETURNS`, `MODIFIES`) are not in CBM's documented vocabulary, not in the binary's string table, and not in any of the three graphs; `EXTENDS` is in the binary only. They should be dropped or re-sourced.
- Both edges the mapping marks `verification_and_mapping` name a triple the catalog does not have. `HANDLES` is written as `application.applicationfunction → api.operation` with `provides`; the catalog has the reverse direction, `api.operation.realizes.application.applicationfunction`. `HTTP_CALLS` is written as `application.applicationservice → api.operation` with `consumes`; the catalog has no `consumes` into `api.operation` from any application type (the nearest are `api.operation.references.application.applicationservice` and `api.operation.references.api.operation`).
- `extraction-heuristics.json` names four DR types that do not exist in the spec: `data-store.table`, `data-store.column`, `data-model.entity`, `data-model.attribute` (the spec has `data-store.collection`, `data-store.field`, `data-model.objectschema`, `data-model.schemaproperty`).
- Ten catalog additions would be needed before the structural edges `INHERITS`, `IMPLEMENTS`, `OVERRIDE`, `EMITS`, `CONTAINS_FOLDER` and the infrastructure edges can map cleanly; each is named in the edge table. The rest of the widening needs no spec change.

### Catalog additions the edge mapping would need

Each of these is missing today; all would be additive relationship schemas (spec change, ask first).

1. `application.applicationcomponent.specializes.application.applicationcomponent` and `application.dataobject.specializes.application.dataobject` (`INHERITS`, `EXTENDS`).

6. `application.applicationcomponent.uses.application.applicationservice` (`CALLS` into a promoted service, without reversing to `serves`).

## Proposed order for widening the mapping

Ordered by cards reached per unit of work, with no-spec-change items first. Each step is one PR against `spec/analyzers/cbm` (and the eval harness where noted); the catalog additions are a separate, ask-first spec change.

1. **Correct what is there.** Rewrite `HANDLES` as `api.operation realizes application.applicationfunction` (direction and predicate); mark `HTTP_CALLS` as blocked on catalog addition 7 (keep it `verification_and_mapping` with an explicit note, or downgrade to `traversal_only` until then); delete the five edges CBM does not emit (`CREATES`, `USES`, `REFERENCES`, `RETURNS`, `MODIFIES`) and note `EXTENDS` as binary-only; fix the four non-existent types in `extraction-heuristics.json`; add the 16 absent labels to `unmapped_labels` so every CBM label is accounted for. Zero new coverage, but it makes the file truthful before anything builds on it.
2. **`Interface` → `application.dataobject`** with three rules: `extends <...>Repository` → `data-store.accesspattern`; file matches `*.gen.ts` or `client/core/**` → drop; otherwise `dataobject`. 97 cards, 79 of them decided deterministically. Add `Type`, `Enum`, `Struct`, `Trait` under the same rules at low confidence.
3. **Structural edges with catalog ids:** `DEFINES_METHOD` → `assigned-to` (227 cards) and `IMPORTS` → `uses` (93 cards), both `verification_and_mapping`, both only between symbols that survive Tier 1. Add `DEFINES` as the provenance edge (`source_reference.file`).
4. **Decorators as evidence.** Add `DECORATES`, `decorators`, `decorator_tags`, `route_method`, `route_path` to `evidence_fields` on `Class`, `Function`, `Method`, and promotion heuristics keyed on them: `Controller`/`RestController` → `applicationinterface`; `Entity`/`Table`/SQLModel `table=True` → `data-model.objectschema` with `data-store.collection`; `Repository` → `data-store.accesspattern`; `Service` → `applicationservice`; `router.<verb>`/`GetMapping`/`route_path` set → `api.operation` for the handler's route; `Test`/`pytest.fixture` → testing. This is what moves the fastapi and petclinic `Class` cards (10 + 9 `objectschema`, 5 controllers) and the 9 petclinic handler methods.
5. **Data access edges:** `USAGE` and `WRITES` → `accesses` to `dataobject` (387 + 40 cards), gated on the target having mapped in step 2.
6. **Behavioural edges:** `CALLS`, `CALL_REFERENCE`, `DATA_FLOWS` → `flows-to` / `depends-on` between kept functions (327 cards), after significance gating, because most methods are `none` in the gold.
7. **Tests:** keep test nodes in a separate pass instead of excluding them, map test functions to `testing.testcasesketch` and `TESTS` / `TESTS_FILE` → `tests` (11 cards here, far more in any real corpus).
8. **Catalog additions 1 to 6**, then `INHERITS`, `IMPLEMENTS`, `OVERRIDE`, `EMITS`, `LISTENS_ON`, `Channel`.
9. **Infrastructure:** `Resource`, `Image`, `Chart`, `Process`, `Package`, `EnvVar` and `DEPLOYS`, `CONNECTS_TO`, `INFRA_MAPS`, `DEPENDS_ON`, `SPAWNS`, after catalog additions 7 to 10 and after adding a corpus that produces these nodes (the fastapi template's Dockerfiles and compose file did not, in the current index; re-index with 0.10.2's infrastructure pass and check `get_graph_schema` first). (Done 2026-11-12 for `Table`, `Resource`, `Image`, `Chart` and `Process` with `INFRA_MAPS`, `DEPENDS_ON`, `SPAWNS` and `DEPLOYS`; see "Infrastructure mapping" above. `Package`, `EnvVar` and `CONNECTS_TO` are not mapped.)
10. Leave unmapped, deliberately: `Variable`, `Constant`, `Macro`, `Section`, `Project`, `Branch`, `Folder` (until step 8's `composes`), and the similarity and history edges.
