# CBM mapping inventory (2026-10-28)

Phase 2 of [EXTRACTION_STRATEGY.md](../EXTRACTION_STRATEGY.md) widens `spec/analyzers/cbm` to the rest of codebase-memory-mcp's (CBM) vocabulary. This document is the starting inventory: every CBM node label and edge type, what `spec/analyzers/cbm/*.json` says about it today, and, for the unmapped ones, the candidate Documentation Robotics (DR) type or predicate checked against the relationship catalog in `spec/dist/*.json`. It changes nothing; it is the list the mapping work is scoped from.

**Progress (2026-10-29):** steps 1 to 4 of the widening order below are applied on the
`feature/phase2-cascade` branch, with two departures from the plan. `HTTP_CALLS` was downgraded to
traversal-only rather than kept with a note, so no relationship-creating edge names a missing
triple. The `Interface` fallback narrows to the application layer only (data object, application
interface, application event), not to data-model as well: Clef put 35 of dr-cli's 60 interfaces in
data-model when it was offered, against a charter-labelled gold that files in-code interfaces as
application data objects. Steps 2 and 4 are Tier-0 rules in `extraction-heuristics.json`, measured
in the Phase 2 results of [EXTRACTION_STRATEGY.md](../EXTRACTION_STRATEGY.md).
`cli/tests/unit/analyzers/cbm-mapping-catalog.test.ts` keeps the mapping consistent with the
catalog from now on.

## Summary

- CBM documents 28 node labels; the mapping names 12 (5 mapped, 7 listed as unmapped). 16 labels are absent from the mapping altogether, including `Variable` (the most numerous node in every corpus), `Decorator`, `Field`, `Section`, `Channel`, `EnvVar`, `Table` and every infrastructure label.
- CBM documents 42 edge types (plus 6 seen only in the binary or UI). The mapping names 13. Of those, five (`CREATES`, `USES`, `REFERENCES`, `RETURNS`, `MODIFIES`) are not in CBM's documented vocabulary, not in the binary's string table, and not in any of the three graphs; `EXTENDS` is in the binary only. They should be dropped or re-sourced.
- Both edges the mapping marks `verification_and_mapping` name a triple the catalog does not have. `HANDLES` is written as `application.applicationfunction → api.operation` with `provides`; the catalog has the reverse direction, `api.operation.realizes.application.applicationfunction`. `HTTP_CALLS` is written as `application.applicationservice → api.operation` with `consumes`; the catalog has no `consumes` into `api.operation` from any application type (the nearest are `api.operation.references.application.applicationservice` and `api.operation.references.api.operation`).
- `extraction-heuristics.json` names four DR types that do not exist in the spec: `data-store.table`, `data-store.column`, `data-model.entity`, `data-model.attribute` (the spec has `data-store.collection`, `data-store.field`, `data-model.objectschema`, `data-model.schemaproperty`).
- Ten catalog additions would be needed before the structural edges `INHERITS`, `IMPLEMENTS`, `OVERRIDE`, `EMITS`, `CONTAINS_FOLDER` and the infrastructure edges can map cleanly; each is named in the edge table. The rest of the widening needs no spec change.

### Catalog additions the edge mapping would need

Each of these is missing today; all would be additive relationship schemas (spec change, ask first).

1. `application.applicationcomponent.specializes.application.applicationcomponent` and `application.dataobject.specializes.application.dataobject` (`INHERITS`, `EXTENDS`).
2. `application.applicationfunction.specializes.application.applicationfunction` (`OVERRIDE`).

5. `application.applicationcomponent.composes.application.applicationcomponent` (`CONTAINS_FOLDER`, directory-level components).
6. `application.applicationcomponent.uses.application.applicationservice` (`CALLS` into a promoted service, without reversing to `serves`).
7. An application-layer source that `consumes` `api.operation` (`HTTP_CALLS`); today only UX and navigation types reach an operation from the consumer side.
8. `application.applicationcomponent.uses.technology.systemsoftware` (`SPAWNS`, `DEPENDS_ON` on packages, without reversing to `serves`).
9. `technology.node.depends-on.technology.technologyservice` (`CONNECTS_TO`) and `technology.node.composes.technology.node` (compose `depends_on`).
10. `technology.artifact.assigned-to.technology.node` (`DEPLOYS`), or accept the reversed `composes`.

## Proposed order for widening the mapping

Ordered by cards reached per unit of work, with no-spec-change items first. Each step is one PR against `spec/analyzers/cbm` (and the eval harness where noted); the catalog additions are a separate, ask-first spec change.

1. **Correct what is there.** Rewrite `HANDLES` as `api.operation realizes application.applicationfunction` (direction and predicate); mark `HTTP_CALLS` as blocked on catalog addition 7 (keep it `verification_and_mapping` with an explicit note, or downgrade to `traversal_only` until then); delete the five edges CBM does not emit (`CREATES`, `USES`, `REFERENCES`, `RETURNS`, `MODIFIES`) and note `EXTENDS` as binary-only; fix the four non-existent types in `extraction-heuristics.json`; add the 16 absent labels to `unmapped_labels` so every CBM label is accounted for. Zero new coverage, but it makes the file truthful before anything builds on it.
2. **`Interface` → `application.dataobject`** with three rules: `extends <...>Repository` → `data-store.accesspattern`; file matches `*.gen.ts` or `client/core/**` → drop; otherwise `dataobject`. 97 cards, 79 of them decided deterministically. Add `Type`, `Enum`, `Struct`, `Trait` under the same rules at low confidence.
3. **Structural edges with catalog ids:** `DEFINES_METHOD` → `assigned-to` (227 cards) and `IMPORTS` → `uses` (93 cards), both `verification_and_mapping`, both only between symbols that survive Tier 1. Add `DEFINES` as the provenance edge (`source_reference.file`).
4. **Decorators as evidence.** Add `DECORATES`, `decorators`, `decorator_tags`, `route_method`, `route_path` to `evidence_fields` on `Class`, `Function`, `Method`, and promotion heuristics keyed on them: `Controller`/`RestController` → `applicationinterface`; `Entity`/`Table`/SQLModel `table=True` → `data-model.objectschema` with `data-store.collection`; `Repository` → `data-store.accesspattern`; `Service` → `applicationservice`; `router.<verb>`/`GetMapping`/`route_path` set → `api.operation` for the handler's route; `Test`/`pytest.fixture` → testing. This is what moves the fastapi and petclinic `Class` cards (10 + 9 `objectschema`, 5 controllers) and the 9 petclinic handler methods.
5. **Data access edges:** `USAGE` and `WRITES` → `accesses` to `dataobject` (387 + 40 cards), gated on the target having mapped in step 2.
6. **Behavioural edges:** `CALLS`, `CALL_REFERENCE`, `DATA_FLOWS` → `flows-to` / `depends-on` between kept functions (327 cards), after significance gating, because most methods are `none` in the gold.
7. **Tests:** keep test nodes in a separate pass instead of excluding them, map test functions to `testing.testcasesketch` and `TESTS` / `TESTS_FILE` → `tests` (11 cards here, far more in any real corpus).
8. **Catalog additions 1 to 6**, then `INHERITS`, `IMPLEMENTS`, `OVERRIDE`, `EMITS`, `LISTENS_ON`, `Channel`.
9. **Infrastructure:** `Resource`, `Image`, `Chart`, `Process`, `Package`, `EnvVar` and `DEPLOYS`, `CONNECTS_TO`, `INFRA_MAPS`, `DEPENDS_ON`, `SPAWNS`, after catalog additions 7 to 10 and after adding a corpus that produces these nodes (the fastapi template's Dockerfiles and compose file did not, in the current index; re-index with 0.10.2's infrastructure pass and check `get_graph_schema` first).
10. Leave unmapped, deliberately: `Variable`, `Constant`, `Macro`, `Section`, `Project`, `Branch`, `Folder` (until step 8's `composes`), and the similarity and history edges.
