# Spec maintainer notes from the enrichment pass

Concerns raised by the model while defining each type (`propose-nodes.ts`) and each source type's relationships (`propose-relationships.ts`), October 2026. These are prompts for review, not decisions.

## Node types

### api

- **callback**: The callback's map-key name (e.g. 'onPaymentComplete') has no attribute, and it is unclear whether one node represents a named callback or a single expression entry. The 'uses api.server' relationship is dubious because callback targets are resolved at runtime. The layer description mentions webhooks, but no webhook type exists; webhooks are an OpenAPI 3.1 concept and could be confused with callbacks.
- **components**: The composes→api.paths edge is invalid: an OpenAPI 3.0 Components object has no paths or pathItems, which exist only in 3.1. components.responses holds Response objects, not a Responses map, so drop composes→api.responses. api.response appears under both aggregates and composes; pick one. The oauthflows→components association is spurious, because flows nest in securityscheme.
- **contact**: The definition mentions 'name', but no name attribute is listed; add one, since OpenAPI Contact has name, url and email. The associated-with relationship to api.openapidocument duplicates the path through api.info aggregates. Consider removing it, because Contact is reachable only via Info in OpenAPI 3.0.
- **encoding**: Per OpenAPI 3.0, style, explode and allowReserved apply only to application/x-www-form-urlencoded, and style allows only form, spaceDelimited, pipeDelimited and deepObject. The current style description, which mentions multipart, and its enum (matrix, label, simple) are wrong. 'Handles complex content negotiation' is inaccurate. A 'headers' attribute is missing, and the association with api.parameter is spurious.
- **example**: `value` is typed string but OpenAPI allows any JSON value; it should be `any`. OpenAPI 3.0 RequestBody and ServerVariable have no examples field, so those relationships are non-standard. Example→operation association is also not in OpenAPI 3.0. No attribute captures the map-key name of the example.
- **externaldocumentation**: Incoming 'references' from api.pathitem and api.paths, and the outgoing 'associated-with' to api.info, have no basis in OpenAPI 3.0: those objects have no externalDocs field. A 'serves' edge to api.tag is missing. Schema.externalDocs is typed object while OpenAPIDocument.externalDocs is typed string. Make both consistent reference types.
- **header**: The definition's 'request components' wording is misleading: request headers are Parameters (in: header). The definition mentions a 'name' attribute that is not listed. OAS 3.0 restricts header style to 'simple' and applies allowEmptyValue and allowReserved only to query parameters. The enum and those two attributes should be narrowed or removed.
- **info**: The api.externaldocumentation → api.info relationship has no OpenAPI 3.0 basis, because Info has no externalDocs field; it belongs on api.openapidocument. The outgoing info→openapidocument 'associated-with' edge duplicates the incoming 'composes' edge. The contact and license string attributes duplicate the aggregates relationships.
- **license**: The required OpenAPI 'name' field is not listed as an attribute; it is presumably carried by the element's generic name, which should be stated explicitly. The outgoing associated-with link to api.openapidocument duplicates the path via api.info aggregation and may be redundant.
- **link**: The outgoing references to api.tag and api.schema have no basis in the Link Object; consider removing them. The 'uses api.server' relationship reflects the Link 'server' field, which is missing as an attribute. Links attach to a Response, not to Responses, so the api.responses→api.link edge is questionable. Modellers may confuse this with HAL-style payload links.
- **mediatype**: The 'examples' map is referenced in the 'example' description but is not modelled as an attribute; add it or rely on the api.example relationships. 'example' is typed string but OpenAPI allows any value. Duplicate relationship pairs, aggregates and composes toward encoding, also aggregates and references toward example and schema, are ambiguous. The associated-with relationship to api.header has no OpenAPI basis, since headers belong to Encoding or Response.
- **oauthflow**: The grant type is implied only by the parent field; consider an explicit flowType enum for classification. Outgoing relationships to api.tag (aggregates), api.ratelimit, api.server and api.operation (serves) look spurious—an OAuth flow is consumed only via its SecurityScheme. OAuthFlows both aggregates and composes OAuthFlow; keep composes only.
- **oauthflows**: The type has no attributes for its four grant-type slots. As a result, the grant type of each child OAuthFlow cannot be recorded anywhere, although api.oauthflow says the type is implied by the parent slot. Consider modelling the slots as an attribute or as a relationship qualifier. The oauthflows→oauthflow link is listed as both 'aggregates' and 'composes'. The associations to operation and components look spurious.
- **openapidocument**: Reference attributes (info, servers, components, tags) are typed string but duplicate the composes/aggregates relationships; pick one mechanism. servers and tags should be arrays. Outgoing composes to api.responses and api.schema contradict OpenAPI, where these live under Components or Operations, not the root. Info→document 'associated-with' duplicates document→info 'composes'.
- **operation**: OpenAPI 3.0 makes operationId, summary and tags optional; marking them required here will reject valid specs. tags should be an array, not a string. http_path duplicates the parent PathItem key. There is no security attribute, although the definition discusses it. The outgoing 'composes api.paths' edge is inverted. Operations inside callback PathItems are ambiguous.
- **parameter**: The required OpenAPI 'name' field is missing, yet (name, in) forms the parameter's identity. The outgoing 'references' relationships to api.tag and api.operation look wrong: parameters do not reference tags, and operation→parameter already exists as an aggregates relationship. Also, 'example: any' sits uneasily beside the api.example relationship.
- **pathitem**: No attribute holds the path template itself (the map key) or the PathItem-level $ref. api.operation duplicates the path in http_path. Cross-layer relations (realizes businessfunction, requires securitypolicy, depends-on technologyservice) overlap with the same relations at operation level. The pathitem→pathitem 'references' relation stands in for $ref but is listed twice.
- **paths**: Several relationships do not match OpenAPI 3.0: the Paths Object holds no servers, tags, externalDocs or rate limits (servers belong to PathItem/Operation); api.components does not contain paths; 'api.operation composes api.paths' inverts containment. The duplicate aggregates/composes edges to api.pathitem should be reduced to composes. Consider allowing x- extension keys.
- **ratelimit**: Not an OpenAPI 3.0 construct, so the layer's standard does not ground it. scope and keyBy overlap; for example, per-ip duplicates keyBy 'request.ip'. Consider deriving one from the other. The window format is unspecified; ISO 8601 duration is suggested. A burst/capacity attribute is missing for token-bucket limiters. The 'governs' and 'serves' relationships to api.operation look redundant.
- **requestbody**: The required 'content' map has no attribute; it exists only via the mediatype relationships. Both 'aggregates' and 'composes' to api.mediatype are declared, plus 'mediatype serves requestbody', which is redundant and inconsistent; pick one. Direct links to api.example, api.schema and api.encoding bypass MediaType, where OpenAPI actually places them.
- **response**: No attribute holds the HTTP status code, which is only the map key in api.responses; consider a statusCode attribute. Relationships to api.header and api.mediatype appear as both aggregates and composes, which is redundant. 'api.mediatype --serves--> api.response' reverses the natural direction. Also, api.responses wrongly says 2XX ranges are unsupported; OpenAPI 3.0 allows 1XX–5XX.
- **responses**: Current definition is wrong: OpenAPI 3.0 permits uppercase ranges 1XX-5XX as keys; fix it. The openapidocument→responses and components→responses relationships are invalid (no root Responses; components.responses holds Response objects). aggregates header/schema and references link belong on api.response. Consider a 'statusCodes' attribute listing defined keys.
- **schema**: OpenAPI 3.0 uses an extended subset of JSON Schema Wright Draft 00, not Draft 7; correct this. The word 'inline' conflicts with components composing schemas. 'type' needs an enum. 'default' should be typed any and 'enum' typed array. Validation keywords are missing: minimum/maximum, minLength/maxLength, pattern, additionalProperties, not, minItems/maxItems. Boundary with data-model.jsonschema needs a rule.
- **securityscheme**: Missing 'name' attribute (the header/query/cookie key name), which is required for apiKey and cited in the definition. 'in' should be enum[header|query|cookie]. There is no element type for security requirement objects. Outgoing maps-to data-store.collection and serves business.businessrole look speculative and invite misclassification.
- **server**: 'variables' is typed string but is a map to api.servervariable; make it an object or rely on the aggregates relationship alone. The outgoing 'references api.securityscheme' has no OpenAPI basis, since servers do not bind security. 'serves application.applicationcomponent' inverts the usual dependency and should be reviewed. Deployment hosts belong to technology.node; api.server is only the declared URL.
- **servervariable**: Attribute 'enum' is typed string but OpenAPI requires a non-empty array of strings. There is no explicit name attribute, although the map key is the identity. The outgoing relationships 'serves api.operation', 'associated-with api.parameter' and 'references api.example' have no basis in OpenAPI. 'governs api.server' duplicates the inverse 'aggregates'. Review these relationships.
- **tag**: The required 'name' attribute is missing; it is the tag's identity in OpenAPI 3.0 and needs an explicit attribute plus a uniqueness constraint. Tag→operation 'aggregates' and 'serves' duplicate operation→tag 'aggregates' and 'references'. The oauthflow→tag, parameter→tag, schema→tag and paths→tag edges have no OpenAPI basis. An externalDocs attribute or relationship should be made explicit.

### apm

- **alert**: OpenTelemetry defines no alerting concept, so this type has no standard anchor. Missing attributes: pending/'for' duration, labels, runbookUrl and the hosting tool (dashboard has 'tool'). There is no SLO type even though the layer scope mentions SLOs, so burn-rate alerts lack a target. The 'dashboard monitors alert' relationship is semantically odd; 'displays' would fit better.
- **dashboard**: OpenTelemetry defines no dashboard concept, so standard_reference is null. Panels are an untyped array; consider a panel schema (title, query, visualization type, signal reference) so 'monitors' relationships can be derived. Enum lacks kibana, honeycomb, splunk, prometheus console. The 'monitors' relationship to apm.alert is semantically odd; 'displays' fits better.
- **exporterconfig**: Definition mentions batching and retry, but no attributes exist and batching belongs to span/log processors; drop or add timeout/retry attributes. Protocol should be an enum (grpc|http/protobuf|http/json). Missing headers and signal (traces|metrics|logs). 'logging' is deprecated in the Collector (now 'debug'). endpoint should not be required for stdout.
- **instrumentationconfig**: 'type' (free string, required) overlaps confusingly with 'instrumentationType'; constrain it with an enum or rename it to 'category'. The type lacks a 'libraryVersion' attribute and an 'options' object for settings such as ignored paths or captured headers. Granularity should be fixed at one instance per instrumented library or code path, not one per SDK bootstrap.
- **instrumentationscope**: No explicit 'name' attribute although OTel scope identity is name+version+schemaUrl; add it. droppedAttributesCount being required is a runtime artifact, awkward for design-time models; make optional. The 'aggregates exporterconfig' relationship is questionable: exporters are provider-level, not per scope. The attributes description says 'this signal', but a scope is not a signal.
- **logconfiguration**: serviceName conflicts with TraceConfiguration's stated rule that service identity belongs on Resource; consider removing it and relying on the depends-on Resource link. The minimumSeverity enum collapses OTel's 24-level severityNumber scale into six SeverityText names. No attribute captures attached processors or exporters inline; the aggregates relationships carry that information. The 'monitors business service' link is questionable.
- **logprocessor**: Batch tuning attributes are missing (maxQueueSize, scheduleDelayMillis, maxExportBatchSize, exportTimeoutMillis). The type enum does not distinguish Collector processors (filter, attributes, transform) from SDK processors. Relationships flows-to apm.span and metricinstrument→logprocessor look semantically wrong. There is no SpanProcessor counterpart type; span processors are buried in traceconfiguration.
- **logrecord**: The type lacks traceId and spanId, so the claimed trace correlation is not expressible; it also lacks eventName. severityNumber should be an integer constrained to 0–24. The required instance-level fields (timestamps, flags) conflict with modelling design-time log event types. Consider making them optional, or splitting the type into a log event definition versus a record instance.
- **metricconfiguration**: serviceName duplicates Resource service.name, inconsistent with TraceConfiguration which moved service identity to Resource. Definition cites 'MeterConfig', which does not exist in this layer. Export interval/timeout are reader properties, not MeterProvider ones. No attributes for views, aggregation temporality, or reader type. 'serves apm.resource' relationship direction looks inverted.
- **metricinstrument**: No explicit name attribute, though OTel instrument names have syntax rules. There are no attributes for recorded attribute keys (dimensions) or histogram bucket boundaries (advisory parameters). Prometheus Summary has no enum value. The relationships flows-to logprocessor, flows-to span, and span composes metricinstrument look semantically wrong for the OTel model.
- **resource**: serviceName also appears on logconfiguration and metricconfiguration, which contradicts traceconfiguration's statement that identity belongs on Resource. Remove it there. droppedAttributesCount is rarely observable from code, so it should be optional with a default of 0. The 'aggregates exporterconfig/metricinstrument/span' relationships misstate the model: exporters attach to providers, and signals reference resources rather than being owned by them.
- **span**: Runtime-instance fields (traceId, spanId, parentSpanId, traceState, timestamps, dropped counts) are required, but design-time span definitions extracted from code cannot supply them; make them optional. parentSpanId cannot be required for root spans. droppedEventsCount and droppedLinksCount should be integers, not strings. The span 'composes' traceconfiguration and metricinstrument relationships look inverted.
- **spanevent**: The event 'name' is missing as an attribute, even though OTLP requires it and the definition relies on name='exception'; add it as required. The 'triggers apm.metricinstrument' and 'monitors ux.actioncomponent' relationships are dubious, because events neither drive instruments nor monitor UI directly. The OTel Events API now emits LogRecords, which blurs the boundary with apm.logrecord.
- **spanlink**: Missing OTLP Link 'flags' (sampled/isRemote). traceId/spanId duplicate the references→apm.span relationship; state which one is authoritative. The definition says 'different trace', but links may target spans in the same trace. On Span, droppedLinksCount and droppedEventsCount are typed string while droppedAttributesCount is integer; use integer for all three.
- **traceconfiguration**: The span processor pipeline is in the definition but has no attribute; add processor type (simple|batch), batch size and schedule delay, plus span limits. propagators should be an enum (tracecontext, baggage, b3, b3multi, jaeger, xray). The aggregates→span, aggregates→metricinstrument and span composes→traceconfiguration relationships confuse configuration with emitted instances and should be reviewed.

### application

- **applicationcollaboration**: Rarely maps to a single code symbol, so a classifier will seldom match it from a state card. ArchiMate assigns a collaboration to an interaction, but the spec models this as depends-on/delivers-value; consider an 'assigned-to' relationship. The parallel aggregates and depends-on links to applicationcomponent are redundant. A 'members' or minimum-cardinality constraint is missing.
- **applicationcomponent**: The attribute named 'type' collides with the element-type concept and mixes two axes: ownership (internal/external) and style (service-component), with 'generic' as a catch-all. Consider splitting it into 'sourcing' and 'kind'. Granularity is unclear: are plain classes components or should only deployables qualify? The self 'uses' relationship is listed twice.
- **applicationevent**: Event payload classes blur with dataobject; the specification should state that the published type is the event, with an optional dataobject for a reusable payload. The eventType enum has no value for user or UI-originated events. Topic or channel name and payload reference are missing as attributes. The data-store.eventhandler triggers applicationevent direction looks inverted.
- **applicationfunction**: The phrase 'for internal purposes' conflicts with the realizes→ApplicationService relationship; clarify that the function is the internal behavior that realizes the service, not the exposed contract. The spec needs a granularity rule, otherwise every private method qualifies. The api.operation→realizes→applicationfunction direction looks inverted; operations normally realize or serve services.
- **applicationinteraction**: Lacks the 'properties' attribute every sibling has. The 'pattern' enum overlaps: 'event-driven' and 'publish-subscribe' are hard to separate. Saga/orchestration styles are missing. Single code symbols usually implement one side only, so classifiers will rarely match this type directly. Both realizes and delivers-value point to applicationservice, which is redundant. Collaboration depends-on interaction looks inverted.
- **applicationinterface**: The protocol enum mixes protocols with architectural styles (REST, GraphQL). HTTP/HTTPS splits on TLS, which contradicts the attribute's own guidance. It lacks CLI, Kafka, MQTT and in-process/library APIs. Having both depends-on and serves to applicationservice is redundant. The boundary with the api layer needs stating: contract files go there, runtime bindings go here.
- **applicationprocess**: There are no attributes for trigger, steps or outcome, so the ordered nature that defines this type cannot be captured structurally. Consider adding a 'steps' list and an optional 'executionMode' attribute (sync/async/batch/long-running). Both application processes and application functions use delivers-value toward a service. The relationship names in this layer are non-ArchiMate (depends-on rather than access/assignment).
- **applicationservice**: In code, a @Service class is often both component and service. Classifiers need a rule: model the exposed contract as service and the deployable unit as component. serviceType mixes timing (synchronous/asynchronous) with style (event-driven/batch), so the values overlap. 'applicationinterface depends-on applicationservice' duplicates 'serves' and should be reviewed.
- **dataobject**: No attribute captures structure (fields), mutability or kind (DTO, value object, command). Boundary with data-model.objectschema, persistence entities and API schemas needs an explicit precedence rule (ORM-mapped → persistence; published schema → api/data-model). Event payload classes straddle applicationevent. The self-referencing 'realizes' relationship has unclear semantics.

### business

- **businessactor**: The relationship businessrole --serves--> businessactor departs from ArchiMate, where a role is reached only by assignment from an actor. The actor --serves--> motivation.stakeholder relationship should probably be association. The businessfunction definition says functions are 'performed by an actor'; ArchiMate assigns both processes and functions to actors or roles. Consider adding an internal/external attribute.
- **businesscollaboration**: The 'composes' relationship to BusinessRole conflicts with ArchiMate, which uses aggregation because roles exist independently of the collaboration. ArchiMate 3.2 also allows actors as participants; the definition says only roles. 'performs' should map to ArchiMate assignment. BusinessInteraction's sibling definition misstates that functions are performed by actors.
- **businessevent**: businessrole --triggers--> businessevent is invalid in ArchiMate, where triggers links behavior only; use assignment or drop it. The enum mixes origin (internal/external) with mechanism (message/timer), so it cannot express an external message. The name 'type' collides with the element type. The definition should add BusinessInteraction to match the relationships.
- **businessfunction**: BusinessInteraction's definition says functions are 'performed by an actor' while this layer's relationships use roles; align wording. 'realizes motivation.goal' contradicts 'not goal-oriented'; ArchiMate core elements realize requirements and influence goals. 'serves businessrole' is unusual for a function. The capability-vs-function boundary with product.capability needs explicit guidance.
- **businessinteraction**: The current definition wrongly says BusinessProcess is performed by a role and BusinessFunction by an actor. ArchiMate lets either be assigned to actors or roles. The 'serves → businessservice' relationship is non-standard: ArchiMate behavior realizes services. A 'realizes' relationship is missing. Consider a 'participants' attribute or an explicit minimum-two-roles constraint.
- **businessinterface**: Outgoing accesses/flows-to to BusinessObject and triggers to BusinessProcess/BusinessFunction are not direct ArchiMate relationships for an active structure element. Interface–service is 'assigned-to', not 'provides'. Links from api.operation risk conflating this type with ApplicationInterface. Consider a 'channelType' enum (in-person, phone, web, mail, partner).
- **businessobject**: In ArchiMate, Contract is a specialization of BusinessObject, but here they are modelled as siblings. The 'contract --accesses--> businessobject' relationship (passive accessing passive) is invalid and should be aggregation or specialization. 'composes' is listed twice. The 'messages' example overlaps with businessevent type=message. Consider dropping 'contracts' from the examples.
- **businessprocess**: The incoming 'businessservice realizes businessprocess' is inverted relative to the outgoing 'businessprocess realizes businessservice'; keep only the latter. 'businessprocess aggregates application.applicationprocess' breaks layer independence and should probably be 'applicationprocess realizes/serves'. 'businessrole assigned-to' and 'performs' are duplicates. The BusinessInteraction sibling definition wrongly implies functions are actor-only and processes role-only.
- **businessrole**: The model has both 'performs' and 'assigned-to' from role to process/function, which is redundant because ArchiMate uses assignment only. 'role serves actor' has no ArchiMate basis. The BusinessInteraction definition wrongly implies processes are performed by roles and functions by actors. Inbound security.role maps-to invites conflating access-control roles with business roles.
- **businessservice**: The outgoing 'businessservice realizes businessprocess' relationship inverts ArchiMate, which has the process realize the service, and it duplicates the existing incoming edge. 'delivers → businessobject' is non-standard; ArchiMate would use access. 'data-store.database realizes' and 'technology.systemsoftware realizes' skip the application layer. Consider adding optional serviceLevel and consumer attributes.
- **contract**: ArchiMate treats Contract as passive structure, so the outgoing serves, triggers, and accesses relationships are invalid. Passive elements are accessed; they do not act. Consider modelling Contract as a specialization of BusinessObject. It also lacks structured attributes (parties, effectiveDate, expiryDate, version) that would help classification.
- **product**: The current definition misclassifies Product as passive structure; in ArchiMate 3.2 it is a composite element. Relationships cover only business services and contracts. ArchiMate also lets products aggregate application and technology services, business objects and data objects. No attributes exist for target market, pricing model or lifecycle status. Classifiers will confuse e-commerce 'Product' entity classes with this type.
- **representation**: The format enum mixes media types with serialization formats and has no values for paper/print, spreadsheet (xlsx/csv), image, or email. On-screen forms fit poorly under 'html'. Consider aligning the values with MIME types or adding 'paper' and 'other'. Without guidance, application-layer DataObject serializations such as JSON API payloads risk being modelled as Representation.

### data-model

- **arrayschema**: 'type' is typed 'any' and optional. It should be a required string fixed to 'array'. 'items' as a string cannot express Draft 7's tuple form (an array of schemas). 'additionalItems' is missing. The aggregates relationships omit arrayschema→arrayschema (nested arrays) and boolean element types.
- **jsonschema**: type is marked required, but Draft 7 root documents may omit type (e.g. root of pure definitions or a composition); consider making it optional. Missing description attribute, unlike siblings. Relationships to motivation.goal and business.businessservice look overreaching for a schema document. Overlap with api.schema via realizes should be clarified.
- **numericschema**: Unlike StringSchema and ArraySchema, 'type' here is a required enum; align siblings, which use 'any'. No 'format' attribute exists for int32/int64/float/double hints, which OpenAPI-derived code commonly carries. Overlap with SchemaProperty, whose type enum includes number/integer: specify whether inline field bounds create a separate NumericSchema element or stay on the property.
- **objectschema**: type should be a const 'object', not a free string. additionalProperties, patternProperties and propertyNames are typed string but Draft 7 allows boolean/schema or regex-to-schema maps. The properties attribute duplicates the aggregates→schemaproperty relationship; pick one. Draft 7 'dependencies' keyword is missing. realizes→motivation.goal looks semantically wrong.
- **reference**: The maps-to application.applicationservice relationship looks wrong, because a schema pointer does not realise a service. SchemaProperty also carries a $ref attribute, so the boundary is fuzzy. There is no attribute that distinguishes internal fragment references from external URI references. The 'references' target is limited to schemadefinition, but a $ref may also point at a jsonschema root or another external schema.
- **schemacomposition**: No discriminator attribute exists for oneOf variants (OpenAPI discriminator, Pydantic discriminator), so tagged unions lose their tag. The 'not' attribute is typed string but holds a subschema; the outgoing composes relationships carry the real link. No composes edge to data-model.reference, although subschemas are usually $refs. Draft 7 if/then/else conditional keywords have no home type.
- **schemadefinition**: Object-typed definitions have no properties or required attributes, so they must defer structure to objectschema. The spec does not say whether that is via composes or aggregates. No attribute holds the definitions key, which is the actual $ref target; title is only an annotation. The enum attribute is an array here but a string on schemaproperty. Draft 2019+ '$defs' is not mentioned.
- **schemaproperty**: Several attributes are typed string but hold other JSON values: enum and examples are arrays, and default and const are arbitrary JSON. Siblings type enum as array, so the types are inconsistent. There is no per-property required or nullable flag; required lives on objectschema. The format attribute lacks the enum that stringschema.format has. The property name is implicit in the element name.
- **stringschema**: The format enum mixes in post-Draft-7 values: duration and uuid come from 2019-09, and Draft 7's uri-template is missing. Change type from 'any' to const 'string'. Format is duplicated on schemaproperty and schemadefinition, which blurs ownership. String enum/const have no home here, so they get modelled on schemaproperty.

### data-store

- **accesspattern**: targetCollection duplicates the accesses→collection relationship, and accesses and aggregates→collection overlap; pick one. A single targetCollection cannot express join or multi-collection transaction patterns. The patternType enum lacks DELETE. Consider adding projection (returned fields), pagination/limit, and a latency target attribute.
- **collection**: The Elasticsearch index is assigned both to namespace and to collection (SEARCH_INDEX). The graph NODE_LABEL value collides with field fieldRole LABEL. collectionType should probably be required. The outgoing 'collection composes namespace' relationship appears inverted. Per-key Redis structures (HASH, SORTED_SET) need a granularity rule: model the key pattern, not each key.
- **database**: The boundary between server instance and logical database is unclear: one PostgreSQL server can host many databases. Consider adding an endpoint or host attribute. The composes edges to field, index and validationrule bypass collection and duplicate containment. MongoDB's 'database' maps to namespace, which conflicts with its name. deploymentModel overlaps technology.node topology.
- **eventhandler**: WATCHER and ALERT_RULE fire on periodic conditions, not data changes, and timing lacks a SCHEDULED/PERIODIC value. events has no item enum. Boundary with application-layer consumers (a service calling watch()) is unclear; specify whether the subscription or the consumer is modelled here. field --triggers--> eventhandler should probably be 'monitors' (UPDATE OF column).
- **field**: nullable duplicates validationrule NOT_NULL, so state which is canonical. fieldRole LABEL overlaps collection NODE_LABEL. fieldRole lacks a PRIMARY_KEY/ID value, and VALUE versus PROPERTY is ambiguous for graphs. Composition of field by database and namespace should probably be restricted to collection. A field-level 'description/comment' attribute is missing.
- **index**: The method enum mixes access methods with key shapes: COMPOUND/MULTIKEY are orthogonal to BTREE. The fields attribute is a plain string, with no per-field sort direction or opclass. The Elasticsearch 'index' is claimed by both the collection and namespace definitions. Unique indexes overlap with ValidationRule UNIQUE. AccessPattern→Index has redundant aggregates and uses relationships.
- **namespace**: The mapping of an Elasticsearch index to Namespace conflicts with Collection's SEARCH_INDEX type; pick one. The relationships 'collection composes namespace' and 'namespace composes field' look inverted or skip a level. A Redis prefix is only a convention, not an engine object. Namespace lacks attributes for Cassandra replication strategy and for a per-namespace charset or collation.
- **retentionpolicy**: A single duration and action cannot express multi-phase lifecycles such as ILM hot/warm/cold/delete; consider a phases array. Overlaps with collection.ttlDefault and MongoDB TTL indexes, so the boundary needs a rule. Format mismatch: retentionDuration uses ISO 8601 but downsampleInterval uses '1h'. The 'aggregates' edges duplicate 'governs'. An age-basis field (insert time or timestamp field) is missing.
- **storedlogic**: LAMBDA and language EXTERNAL contradict 'executes within the engine'. DynamoDB Lambda triggers are better modelled as an eventhandler bound to external application code. CONTINUOUS_QUERY overlaps view CONTINUOUS_AGGREGATE and retentionpolicy DOWNSAMPLE. PROCEDURE and STORED_PROCEDURE duplicate each other. A parameters/signature attribute is missing. The 'migrates' relationship to collection is unclear.
- **validationrule**: NOT_NULL duplicates field.nullable, and UNIQUE vs UNIQUENESS_CONSTRAINT is a redundant split; consider merging. TTL_CONSTRAINT overlaps collection.ttlDefault and retentionpolicy. There is no deferrable/initiallyDeferred attribute for SQL DEFERRABLE constraints. NO_ACTION described as 'deferred reject' is accurate only for deferrable constraints. The enforcement enum cannot express MongoDB validationLevel (strict/moderate).
- **view**: 'materialized' is redundant with viewType and can contradict it (e.g. ALIAS with materialized=true); consider deriving it. InfluxDB continuous queries appear both here (CONTINUOUS_AGGREGATE) and under storedlogic CONTINUOUS_QUERY. FILTERED overlaps VIRTUAL. An 'updatable' attribute is missing. The derives-from relationships carry the source collections, so no sourceCollections attribute is needed.

### motivation

- **assessment**: assessmentType mixes methods (SWOT) with subject kinds (risk, gap, impact). It also cannot say which SWOT quadrant a finding belongs to; consider adding a swotCategory attribute and severity/likelihood attributes for risk findings. The relationship list shows assessment-influence-assessment twice; confirm this is intentional and not a duplicate.
- **constraint**: The current definition's phrase 'as opposed to requirements which must be satisfied' is misleading: in ArchiMate constraints are binding too, being a requirement-like element restricting realization. 'external' overlaps 'regulatory'. Consider adding 'contractual/legal' and 'security' values, plus a source/rationale attribute. The self-loop specializes relationship is listed twice.
- **driver**: Category enum mixes overlapping values: 'business' overlaps market/strategic/competitive, and 'technical' duplicates 'technological'. Consider consolidating. There is no internal/external flag even though the definition hinges on it. Consider adding an 'origin' enum. The ArchiMate standard places stakeholder→driver as association, so the incoming 'influence' from stakeholder is non-standard and should be reviewed.
- **goal**: Several relations depart from ArchiMate 3.2 or are questionable: goal→assessment influence, requirement→goal aggregation, goal→value realization, and data-model.jsonschema realizes goal. - **chartseries**: The description mentions 'legend properties' and 'data source', but no legend attributes exist beyond label, and the data source comes from the dataconfig relationship. Mixed-type charts justify a per-series type. There is no attribute for axis assignment or stacking.
- **componentinstance**: Both implements and realizes point to ux.librarycomponent, and renders→librarycomponent duplicates ref; keep one. ref is optional although the definition depends on it, so consider making it required. There is no slot or variant attribute, unlike ComponentReference. Buttons that are library components blur the boundary with ActionComponent. Add a name/label so instances of the same component can be told apart.
- **componentreference**: The 'implements → librarycomponent' relationship is semantically odd for a slot pointer; 'references' fits better. Self-referential 'renders' is listed twice (outgoing and incoming). 'variant' must match variants on the referenced component, but LibraryComponent declares no variants attribute, so this constraint is unverifiable. Consider a 'props' override, or state explicitly that props are not permitted.
- **dataconfig**: The definition mentions 'transformation pipelines' and 'update triggers', but no attributes exist for transform, refresh or polling interval, cache policy or invalidation. 'target' is described as the destination, yet its examples (an API endpoint, a data-model entity) are sources; binds-to relationships already identify the receiving component. The 'realizes ux.statepattern' relationship is doubtful.
- **errorconfig**: The description promises retry behavior, fallback content and user guidance, but no attributes model them. notificationType includes 'success', which does not fit an error configuration. Nothing maps error codes or api.response statuses to messages despite the maps-to relationship. The difference between errorMessage and defaultErrorMessage should be stated in the spec.
- **experiencestate**: channel duplicates UXSpec.experience with a different enum (web/mobile vs visual). No final/terminal flag or parent-state attribute for hierarchical statecharts. Outgoing associated-with, governs and renders to ux.view overlap; pick one. 'specializes' to statepattern is semantically wrong (state is a member, not a subtype); chartseries 'uses' experiencestate looks spurious.
- **layoutconfig**: The definition promises responsive breakpoints, but there is no breakpoint attribute. justifyItems should use the CSS Grid values start/end, not flex-start/flex-end. 'absolute' and 'sticky' are position values, not display modes. The 'style' enum duplicates 'grid'. labelPosition is form-specific. ux.view.layout (string) overlaps this type, and the self-'composes' relationship is listed twice.
- **librarycomponent**: The type enum has no 'action' or 'button' category, so button-like library components are classified ambiguously against ActionComponent. The renders and composes self-relationships overlap, as do the implements and realizes relationships from ComponentInstance. Consider adding 'variants' (ComponentReference.variant depends on it) and 'version' attributes.
- **librarysubview**: Both 'aggregates' and 'composes' to componentinstance are redundant; keep one. Likewise subview 'realizes' vs 'uses' librarysubview, and uxlibrary 'aggregates' vs 'provides'. There are no layout, dataConfig or slot/parameter attributes, so consumers cannot override instance props when embedding. The category is free text, whereas sibling categories are enums.
- **stateaction**: The action enum lacks scroll and focus, although the examples (scroll-to-top, focus-first-field) need them. timing 'conditional' refers to a guard, but no guard attribute exists. 'immediate' is defined as running before the state activates, which is meaningless for on-exit. HTML 5.3 has no equivalent; the closest concept is UML 2.5 state entry/exit/effect behaviors.
- **stateactiontemplate**: The action enum (navigate|submit|open|close|dispatch|validate) has no values for the scroll-to-top and focus-first-field examples; consider adding scroll and focus. 'implements' and 'provides' to stateaction plus incoming 'specializes' are redundant, and 'implements' points the wrong way. The definition says 'state transitions' but on-enter/on-exit hooks also apply. The parameters item schema is unspecified.
- **statepattern**: HTML 5.3 has no state-machine concept; W3C SCXML would be a better reference. The initial state is marked twice, by 'states' ordering and by ExperienceState.initial, so the two can conflict. There is no 'parameters' attribute, though patterns like tab-panel need N. The 'form' and 'multi-step' categories overlap. ExperienceState→specializes→StatePattern is semantically odd. The self-specializes relationship is listed twice.
- **statetransition**: The trigger enum has no keyboard value, although ActionPattern has one. It also has no timeout or data events (API success or failure), and 'load' is a weak proxy for these. 'to' is optional even though every edge needs a destination, and it duplicates the navigates-to relationship. TransitionTemplate's required to/trigger attributes blur its motion-only role. Navigation-layer NavigationTransition overlaps this type for route changes.
- **subview**: Inline mode lacks a 'components' attribute (LibrarySubView has one), so the inline composition is only expressible via relationships. Several relationships duplicate each other: aggregates/renders componentinstance; ref, realizes and uses librarysubview; view aggregates/composes subview. accesses data-store.collection and realizes business.businessprocess bypass the application layer and look misplaced.
- **tablecolumn**: No boolean 'sortable' or 'filterable'/'resizable'/'hidden' attributes exist; defaultSortDirection 'none' conflates not-sortable with unsorted. filterType enum mixes operators (equals, range) with widget kinds (multiselect, boolean). 'HTML 5.3 form input filter patterns' is not a real standard clause. The renders→componentinstance relationship overlaps displayType for custom cell renderers; clarify precedence.
- **transitiontemplate**: Required 'to' contradicts reusability, because a template bound to one destination duplicates StateTransition.to. Make 'to' optional, or redefine it as a lifecycle target. 'trigger' is free text while StateTransition.trigger is an enum, so align them. Consider adding delay, direction and iteration attributes. The name invites confusion with StateTransition; 'MotionTemplate' would be clearer.
- **uxapplication**: The channel enum (web|mobile|...) differs from UXSpec.experience (visual|voice|chat|sms); the overlap between 'web'/'mobile' and 'visual' is undocumented. 'experiences' duplicates the aggregates relationship to UXSpec. designSystem accepts either a free identifier or a uxlibrary specNodeId; it should be a reference relationship. A name/identifier attribute is missing, as is an entry-point or source reference like View.source.
- **uxlibrary**: Relationships aggregates and provides are duplicated toward the same targets; pick one semantics. uses→uxlibrary appears twice. No relationships exist to statepattern or actionpattern despite matching array attributes. uxapplication.designSystem references a uxlibrary via a string but no relationship exists. Consider adding a dependencies attribute for library-to-library use.
- **uxspec**: The experience enum (visual|voice|chat|sms) does not align with the channel enum (web|mobile|voice|chat|sms) used by UXApplication, ActionComponent and ExperienceState; 'visual' conflates web and mobile. Granularity is undefined: 'complete' should be replaced by a rule (one per journey or feature). The governs→errorconfig relationship has no matching attribute.
- **view**: Definition says 'routable', yet the routable boolean allows false; clarify that non-routable modals are still views. 'A complete user experience' collides with ux.uxspec. The free-text layout attribute duplicates the applies/uses relationships to ux.layoutconfig. aggregates and composes to ux.subview are redundant. The source object needs a schema (path, symbol, repository).

## Relationships (per source type)

### api

- **callback**: callback uses server is questionable: a callback's target URL normally comes from the runtime expression, not a declared server. Any servers override lives on the callback's PathItem or operation, so this link duplicates a pathitem-to-server relationship and is better derived transitively through aggregates pathitem.
- **components**: Response appears under both aggregates and composes, so the two edges are redundant and contradictory. The composes.paths edge is wrong: Paths is a root sibling of components. The composes.responses edge is wrong: components holds Response entries, not operation-scoped Responses maps. Registry entries use aggregates for some kinds and composes for others, with no clear basis for the difference.
- **contact**: Contact is structurally nested in the Info object, which the document composes, so associated-with to OpenAPIDocument is an indirect shortcut. A composes/aggregated-by relationship with api.info would express the containment more precisely. This document-level link may then be redundant.
- **encoding**: associated-with MediaType understates the link: MediaType composes its encoding entries, so this should be expressed as composition from MediaType. associated-with Parameter has no basis in OpenAPI 3.0, because encodings apply only to request-body media types, and it should probably be dropped. composes Header and references Header are not redundant: the first is an inline declaration, the second a $ref.
- **example**: In OpenAPI 3.0 an Example Object never points to a Schema; it is only co-located with one. 'references' is therefore an inferred link, not a pointer. 'associated-with' to operation is indirect, since it goes through a parameter, header or media type. A path via those elements may make both relationships redundant.
- **externaldocumentation**: associated-with to Info is questionable: the OpenAPI spec does not let externalDocs attach to Info; it attaches to the root document, which already has a serves relationship, so this link is redundant. Tag, a valid attachment point, has no relationship and appears to be missing.
- **header**: The header-to-securityscheme association is weak. The OpenAPI document has no structural link between them, only an apiKey scheme naming the same header string. This should probably be a derived or inferred relationship rather than a declared one. The specializes relationship is conceptual at the specification level and does not connect two instance-level elements.
- **info**: Info→OpenAPIDocument as associated-with is weak: Info cannot exist without its document (exactly one per document), so the inverse OpenAPIDocument composes Info is the accurate structural relation. Contact and License are also nested and document-bound, so composes may fit better than aggregates unless shared contacts or licenses are intended.
- **license**: Structurally, License is nested inside Info, which is composed into OpenAPIDocument, so this is really transitive containment. A composes relationship from License to Info, or reached through Info, would be more precise. A direct associated-with link to the document is redundant if the Info-to-document composition is already modeled.
- **link**: Link→schema and link→tag have no field in the OpenAPI Link Object; both are only indirect, via runtime expressions or the target operation's tags. Link→tag is especially weak and arguably derivable from link→operation plus operation→tag. Link→server is valid, since Link Object has a 'server' field.
- **mediatype**: aggregates and composes encoding are contradictory; Encoding cannot exist outside its MediaType, so keep composes only. associated-with header is indirect (via Encoding) and redundant. serves requestbody/response misstates structure: RequestBody and Response compose MediaType through their content map; use the inverse composed-of instead.
- **oauthflow**: aggregates tag is dubious: OAuthFlow has no structural link to tags, only an indirect one via scopes on operations. associated-with oauthflows understates a real composition: the container owns the flow. serves securityscheme is also really composition via OAuthFlows, not a service. associated-with ratelimit lacks any spec basis beyond gateway conventions.
- **oauthflows**: aggregates and composes to api.oauthflow are contradictory: OAuthFlow cannot exist outside OAuthFlows, so composes is correct and aggregates should be removed. serves to securityscheme should really be composition, since the scheme composes OAuthFlows. The associations with components and operation are indirect, run through SecurityScheme, and duplicate those paths.
- **openapidocument**: composes responses: a Responses map is scoped to an operation, so it belongs to Operation, not the document. composes schema duplicates the path through Components. depends-on technologyservice belongs to the implementing component, not the document. realizes businessservice skips the application layer. serves stakeholder is weak.
- **operation**: composes api.paths is inverted: Paths contains PathItems containing operations. composes/references api.schema and aggregates/references api.tag overlap (inline vs $ref only). delivers api.response duplicates composes api.responses. realizes goal/outcome should be supports/delivers. realizes and triggers businessprocess overlap.
- **parameter**: parameter→operation is inverted: operations contain parameters, so operation composes/aggregates parameter fits better. parameter→tag has no basis in OpenAPI 3.0, since Parameter Objects have no tags field; consider removing it. parameter→schema would be more precise as constrained-by than references.
- **pathitem**: PathItem has no externalDocs field in OpenAPI; the references-externaldocumentation relationship is only realizable via description links, so it is questionable. Realizing a BusinessFunction directly from a path item is unusual; it's normally the operation or an application service that realizes business behaviour. Serves-applicationcomponent is more naturally expressed at the operation level.
- **paths**: Paths aggregates and composes PathItem redundantly; keep composes, using aggregates only for $ref'd components/pathItems. Paths has no servers, externalDocs or tags fields: those belong to PathItem, Operation or root, so those links are transitive at best. 'serves Operation' misstates containment; Operations belong to PathItem.
- **ratelimit**: governs.api.operation and serves.api.operation overlap; both attach a limit to an operation. 'governs' fits the semantics better. 'serves' toward an operation or path item inverts the usual meaning: a rate limit restricts rather than provides functionality. Consider merging into governs/constrains.
- **requestbody**: aggregates and composes to MediaType are redundant and conflicting; composes is correct, since media types live only inside content. The relationships to Example, Encoding and Schema are indirect: they hang off MediaType, not RequestBody. serves Operation is odd; Operation composes/aggregates RequestBody would better express that the body is part of the operation contract.
- **response**: Header and mediatype each have both aggregates and composes; distinguish as $ref-reused versus inline or drop one. aggregates and references to api.schema overlap; both are also indirect, since OAS 3.0 responses reach schemas and examples only through media types or headers, making these transitive shortcuts of mediatype/header relationships.
- **responses**: Headers, schemas and links properly belong to individual Response objects (or MediaType), not the Responses map; these are transitive shortcuts. aggregates.api.schema and references.api.schema largely overlap—distinguish inline versus $ref or drop one. RateLimit association is indirect and better attached to the operation or a 429 Response.
- **schema**: references→api.operation and references→api.tag have no native OpenAPI 3.0 basis; schemas don't point to operations or tags except via vendor extensions. references→api.schema and specializes→api.schema overlap since both use $ref; restrict specializes to allOf inheritance/discriminator. maps-to collection and field overlap with property-level mapping.
- **securityscheme**: The four references edges to application/business elements are vague; uses.systemsoftware likely overlaps references.applicationcomponent. maps-to targets (Actor, Collection) misuse a schema-mapping predicate; consider authenticates→Actor and accesses→Collection. implements SecurityPolicy overstates it, since a scheme covers authentication only; supports or enforces fits better. satisfies Principle conflicts with the Principle definition, which says it is not directly verifiable; governed-by-principles fits better.
- **server**: aggregates→servervariable should be composes: variables have no existence outside their server. references→securityscheme is not an OpenAPI construct, because security requirements attach to root or operations, not servers. satisfies→securitypolicy is weak for a URL declaration. serves→applicationcomponent has inverted direction: the component is exposed via the server. serves→pathitem overlaps with plain structural scoping.
- **servervariable**: 'governs' understates the link: a server variable is structurally part of its server and cannot exist without it, so 'composes' fits better. The OpenAPI ServerVariable object has no examples field, so 'references api.example' depends on vendor extensions and is questionable. 'serves api.operation' only holds indirectly through api.server and may be redundant.
- **tag**: aggregates and serves both express the same fact for tag→operation: the operation lists the tag name. serves is semantically weak because tags provide no behavior. Consider keeping only aggregates. The two associated-with links to schema and security scheme are indirect, derived via operations, and are likely redundant.

### apm

- **alert**: apm.alert.monitors.api.operation and apm.alert.monitors.api.ratelimit are indirect: alerts actually evaluate telemetry (spans, metrics, logs) describing these API elements, so they may be redundant with span/metric monitoring plus span-to-operation traceability. Consider whether 'evaluates' fits better than 'monitors' for rule-over-telemetry semantics.
- **dashboard**: The api.operation relationship is indirect: dashboards observe telemetry (spans, metrics) about the operation rather than the contract itself, overlapping with monitors span/metricinstrument. Monitors alert is closer to 'references' or 'associated-with', since the dashboard displays alert state rather than observing a running system.
- **exporterconfig**: The serves→database relationship looks inverted. The exporter writes to the database, so depends-on or flows-to would fit better. Serves→resource is also questionable: the Resource is attached by providers, and the exporter merely transports it, so associated-with may suit. Satisfies→retentionpolicy is weak, because retention is enforced by the backend, not the exporter.
- **instrumentationconfig**: references exporterconfig conflicts with the source definition excluding where telemetry is sent; the link is indirect via providers. serves resource is weak: the Resource is per-process and attached by providers, not served by an instrumentation entry. serves instrumentationscope is closer to 'uses' or 'generates' than serving.
- **instrumentationscope**: Aggregating ExporterConfig is questionable: exporters attach to providers or pipelines, not scopes, so the link is indirect. The monitors links blur the definition that scope identifies the instrumenting library rather than the observed subject; a predicate such as instruments, or routing through spans, would be more precise.
- **logconfiguration**: serves apm.resource inverts the natural direction and conflicts with depends-on apm.resource; resource serves the configuration, not vice versa. flows-to and aggregates on exporterconfig overlap. depends-on database duplicates what exporterconfig should express. monitors businessservice skips layers; logs observe application components, not business services.
- **logprocessor**: flows-to span is doubtful: log records normally carry span context for correlation and do not flow into spans, so 'references' would fit better unless log-to-span-event bridging is intended. satisfies SecurityConstraints is a weak fit, since separation and binding of duty are workflow rules a log processor cannot fulfil. Only NeedToKnow-driven redaction plausibly applies.
- **logrecord**: The five 'references' relationships (objectschema, schemadefinition, route, view, span) are loosely typed; span correlation is a core OTel link that may merit a dedicated predicate. objectschema and schemadefinition references overlap heavily. monitors toward applicationservice is weak for a single log record, since logs record events rather than actively observing.
- **metricconfiguration**: serves.apm.resource is semantically inverted and redundant with depends-on.apm.resource: the resource is a passive identity input consumed by the MeterProvider, not a consumer served by it; drop it. aggregates.apm.metricinstrument conflicts with the source definition ('not any individual instrument'); a governs/applies-style predicate would fit better than aggregation.
- **metricinstrument**: flows-to logprocessor and flows-to span are semantically wrong: metrics flow to readers or exporters, not to log processors or spans. Exemplar links are already covered by references span. realizes goal should be supports-goals. maps-to outcome should be measures-outcome. monitors pathitem is redundant with monitors operation. Monitoring errorconfig, threat and the schema types is indirect at best.
- **resource**: monitors (Node, SystemSoftware) is wrong: a Resource passively identifies its host/runtime rather than observing it; references or associated-with fits. serves BusinessProcess is dubious for an attribute set. aggregates ExporterConfig is questionable since exporters belong to providers, not the Resource. references SecureResource is weak and overlaps maps-to ApplicationComponent.
- **span**: composes metricinstrument is dubious: instruments are independent of spans (prefer generates/measures). composes traceconfiguration is inverted; configuration governs many spans (use governed-by). flows-to logprocessor is a weak cross-signal path. references apm.span duplicates aggregates spanlink. monitors objectschema is a stretch; spans observe operations, not schemas.
- **spanevent**: The depends-on links to InstrumentationScope and Resource are indirect: both attach to the parent span or batch, not to the event, so 'inherits via span' is more accurate. monitors→ActionComponent is doubtful because a span event records an occurrence rather than observing a UI control. triggers→MetricInstrument is usually co-emission, not causation.
- **spanlink**: Because the span model element is a code-location definition and not a runtime occurrence, the link really references the span definition whose runtime instances it points to. The span-link-to-carrier ownership (composed-of from span) is not covered here and may need a separate relationship.
- **traceconfiguration**: Aggregating metric instruments is questionable, since TraceConfiguration governs a TracerProvider, not a MeterProvider. Satisfies SecurityPolicy is a weak fit, because an XACML-style access-decision policy is not something a tracing config satisfies, and constrained-by or governed-by would fit better. Monitoring both ApplicationService and BusinessService overlaps. Depends-on Database is indirect, as the dependency really sits with the backend.

### application

- **applicationcollaboration**: delivers-value is a traceability predicate. ArchiMate would use assigned-to for collaboration→interaction and realizes for collaboration→service. depends-on component overlaps aggregates when the target is a member. depends-on interaction partly inverts the performer relationship. provides interface conflicts with the interface definition, which says an interface is owned by a component.
- **applicationcomponent**: assigned-to and composes toward ApplicationFunction overlap; composition between active structure and behaviour is not valid ArchiMate. assigned-to and provides toward ApplicationInterface are redundant; ArchiMate uses composition for component-to-interface. Realizing Goal and Principle directly is questionable, since core elements normally realize Requirements, which in turn realize goals and principles.
- **applicationevent**: Triggering an ApplicationCollaboration is semantically wrong: in ArchiMate, triggers links behaviour elements, while a collaboration is active structure. The event should trigger the collaboration's ApplicationInteraction instead. Using depends-on toward a DataObject is also loose; associated-with, or access via the handling process, expresses an event payload more accurately.
- **applicationfunction**: delivers-value to ApplicationService largely duplicates realizes ApplicationService. depends-on DataObject overlaps accesses DataObject. delivers-value is a traceability predicate meant for business value, so applying it to ApplicationProcess is questionable; consumed-by or serves would fit better.
- **applicationinteraction**: delivers-value to ApplicationService is redundant with realizes and misuses a traceability predicate meant for business value/goals. depends-on ApplicationCollaboration inverts ArchiMate semantics: the collaboration should be assigned-to the interaction. depends-on DataObject would be more precise as accesses.
- **applicationinterface**: delivers-value to ApplicationCollaboration is odd: a traceability value predicate targeting an active-structure grouping; aggregation/assignment fits better. Interface depends-on ApplicationComponent inverts ArchiMate composition (component composed-of interface). depends-on ApplicationService and serves ApplicationService overlap and the latter inverts ArchiMate (service is exposed through/assigned to interface).
- **applicationprocess**: delivers-value is a business-value traceability predicate; process-to-service is classically ArchiMate realizes. depends-on to ApplicationEvent and triggers to ApplicationEvent need direction clarity: inbound trigger vs emission. depends-on to ApplicationCollaboration inverts ArchiMate assignment (collaboration assigned-to process). depends-on to DataObject would be more precise as accesses.
- **applicationservice**: accesses vs depends-on DataObject overlap. realizes Goal is non-standard; supports/supports-goals fits better. realizes Requirement vs satisfies Constraint use inconsistent predicates for similar traceability. flows-to vs depends-on between services may duplicate. Serving a Stakeholder (motivation element) is odd; serve a role/actor instead. AccessCondition is too fine-grained; constrain via a policy rule.
- **dataobject**: The direction of 'composes' is ambiguous: its inverse 'composed-of' implies the source is the part, while ArchiMate and the parallel 'aggregates' make the source the whole; whole-as-source was assumed here. 'realizes' between data objects overlaps with 'specializes' and 'extends' for interface or abstract-type implementation, so a precedence rule is needed.

### business

- **businessactor**: ArchiMate permits access only from behavior (or derived via roles), so actor-accesses links are shortcuts. Contract is a BusinessObject specialization, making accesses-contract largely redundant with accesses-businessobject. Actor-serves-Stakeholder is semantically weak: Stakeholder is a motivation element, ArchiMate allows only association here, and an actor often simply is the stakeholder.
- **businesscollaboration**: The composes relationship to BusinessRole conflicts with ArchiMate semantics. Roles exist independently of any collaboration, so this is aggregation, not composition. The accesses relationship to BusinessObject is a derived shortcut. In ArchiMate, the access normally belongs to the BusinessInteraction the collaboration performs, not to the active structure itself.
- **businessevent**: Triggering a BusinessFunction is semantically weak, because functions have no defined start or sequence. ArchiMate allows it, but it should be read as initiating behavior within the function rather than starting the function itself. Consider modeling the triggered behavior as a process that the function contains.
- **businessfunction**: Function realizes Goal is questionable: ArchiMate lets core elements realize requirements and influence goals, so 'supports' or 'influence' fits better. The composes self-relationship has ambiguous direction (whole vs. part as source); it should be documented explicitly. The function serves role relationship is valid but weak, since roles are typically assigned to functions.
- **businessinteraction**: serves to BusinessService looks semantically off: in ArchiMate an interaction typically realizes a business service, and the service then serves consumers. If a 'realizes' relationship exists or is intended, this 'serves' entry is either misdirected or redundant with it.
- **businessinterface**: flows-to toward a passive BusinessObject is non-standard ArchiMate (flow links behavior/active elements) and largely duplicates accesses. Triggers from an interface is not valid ArchiMate (triggering is between behaviors/events); triggering a BusinessFunction, which has no defined start, is especially doubtful—consider serves or assigned-to via the service instead.
- **businessobject**: The references link from business object to data object is weak. ArchiMate models this as the data object realizing the business object (application.dataobject realizes business.businessobject). Consider replacing it with the inverse realization so the traceability direction and strength are explicit.
- **businessprocess**: accesses and delivers BusinessObject overlap; delivers suits outcome/value targets, while ArchiMate would use access (write). aggregates ApplicationProcess is cross-layer; ArchiMate normally has application process serving or realizing the business process. realizes Goal skips the Outcome/Requirement chain and overlaps with realizes Outcome and satisfies Requirement. flows-to and triggers between processes are distinct but often conflated.
- **businessrole**: assigned-to and performs from BusinessRole to BusinessFunction and BusinessProcess are redundant; ArchiMate expresses both via Assignment. BusinessRole assigned-to BusinessInterface inverts ArchiMate (interface is assigned to role, or role composes interface). BusinessRole serves Stakeholder mixes layers loosely; association is likelier. Role triggers BusinessEvent is non-standard in ArchiMate.
- **businessservice**: realizes BusinessProcess is inverted: in ArchiMate, processes realize services. realizes Goal and satisfies Requirement overlap with traceability predicates such as supports-goals and fulfills-requirements. ArchiMate typically links core elements to goals via influence or requirement realization. delivers-value duplicates the motivation-layer delivers predicate.
- **contract**: Contract is a passive object. In ArchiMate, accesses, serves and triggers originate from behavior or events, not from passive objects. Accesses is likely meant as associated-with or aggregates. Triggers should originate from a BusinessEvent such as 'Contract Signed'. Serves to a role could be associated-with. Governs is appropriate.
- **representation**: Contract is a specialization of BusinessObject, so the contract relationship is technically subsumed by the business-object one. It is kept for explicitness only.

### data-model

- **arrayschema**: The aggregates edges to Reference and SchemaDefinition overlap: an items $ref is a Reference that resolves to a SchemaDefinition, so both edges may be recorded for one link. Consider modelling ArraySchema→Reference and Reference→SchemaDefinition instead. maps-to is a data-layer predicate; describing a response body may better fit a 'references' or 'used-by' relation.
- **jsonschema**: realizes→motivation.goal is weak: a data schema rarely realizes a goal directly; supports/supports-goals fits better. realizes→api.schema could equally be maps-to. The serves relationships to application function and business service are indirect, since passive schemas are normally accessed rather than serving. depends-on SystemSoftware and uses TechnologyService overlap.
- **objectschema**: ObjectSchema realizes Goal is dubious; data structures rarely realize goals directly—supports would fit better. Realizes BusinessObject and realizes DataObject partially overlap with each other. Satisfies SecurityConstraints is weak since the container holds procedural rules. Serves ApplicationComponent and serves ApplicationFunction are redundant with the inverse of the component's uses or accesses relationship.
- **reference**: maps-to application.applicationservice looks misplaced: a $ref adds no content of its own, so any service mapping belongs on the SchemaDefinition it resolves to. The same applies, less strongly, to maps-to api.schema, which duplicates what the resolved definition would map to.
- **schemacomposition**: 'composes' with SchemaDefinition is questionable: a named definition exists independently and is reused through $ref, so 'aggregates' or 'references' fits better than composition. 'serves' (behavioral) is odd for a passive schema; 'used-by' (the inverse of uses) or an ArchiMate access relationship from the function would express this more accurately.
- **schemadefinition**: The three serves relationships to component, function and operation overlap with realizes→dataobject and maps-to→api.schema, which are the more precise links. Also, 'requires' RetentionPolicy is a poor fit: that policy covers security data such as audit logs rather than domain types. 'satisfies' DataClassification would read better as governed-by/constrained-by.
- **schemaproperty**: The five 'references' relationships treat the property's own value subschema as a separate referenced element, yet the property has no meaning apart from it; 'composes' or a typed-by predicate may fit better. satisfies→validationrule overlaps with references→string/numericschema, since both express the same value restrictions.

### data-store

- **accesspattern**: aggregates→collection duplicates accesses and misuses whole-part semantics; a pattern targets, not contains, a collection. aggregates→index overlaps uses→index; uses is correct. aggregates→field is better expressed as references. satisfies→accesscondition is odd: conditions are evaluated by policy checks, not realized by queries. serves→businessfunction skips the application layer.
- **collection**: composes namespace is inverted: namespaces contain collections. Collection-composes-collection is valid only for partitions or subcollections. maps-to requestbody overlaps realizes schema, since request bodies are expressed through schemas. implements secureresource could equally be realizes. serves applicationcomponent and serves applicationservice partly duplicate each other.
- **database**: Composing field, index and validationrule directly from database is redundant with database→namespace→collection composition. Realizes businessservice is doubtful, since a store serves rather than realizes business behavior. Satisfies securitypolicy reads better as governed-by, because the database is a policy target. Depends-on systemsoftware and uses technologyservice overlap, and federates vs replicates need clear distinction.
- **eventhandler**: Triggering a BusinessEvent directly from a data-store handler crosses abstraction levels. The usual chain is handler → ApplicationEvent, which then realizes or flows to a BusinessEvent. Treat the business-level link as derived or optional to avoid redundancy with the application-event relationship.
- **field**: field triggers validationrule is better modelled as constrained-by, because declarative constraints restrict values rather than being initiated by them. field triggers storedlogic partly duplicates the path through eventhandler, which per its definition is the activation wiring that invokes stored logic. satisfies dataclassification conflates labelling a field with complying with the tier; a classified-as predicate would be clearer.
- **namespace**: Composing field is redundant and transitive: fields belong to collections, which already compose them. Index and validationrule composition partly overlaps collection-level ownership. Namespace-composes-namespace conflicts with the 'inside a single database instance' definition unless the engine has nested hierarchies (catalog.schema). Composing storedlogic lacks the data-store. prefix in its id.
- **retentionpolicy**: Aggregates and governs toward Collection and Namespace are redundant. A policy does not contain containers as parts; it scopes and rules them, so governs is the correct predicate and aggregates should be dropped. Satisfies toward security.retentionpolicy holds only when the maximum age is not shorter than the security policy's minimum retention period.
- **storedlogic**: Aggregating collections and fields is dubious: stored logic references but does not group them; accesses covers this. Composing a validation rule contradicts its definition (declarative schema constraint, not part of procedural code). Validates (a testing predicate) overlaps accesses and imperative triggers excluded from ValidationRule. Realizes business function skips the application layer; implements application function is preferable.
- **validationrule**: cascades-to fits only referential constraints with ON DELETE/UPDATE actions; CHECK, NOT NULL and unique rules never cascade, so this relationship should be limited to foreign-key rules. Satisfies overlaps with the governance predicate enforces-requirement; the spec should pick one predicate for constraint-to-requirement traceability.
- **view**: aggregates→collection largely duplicates derives-from→collection; derives-from is the accurate semantics. aggregates→field is odd since fields belong to persisted collections, not views. realizes→api.response and serves→businessservice skip intermediate application/API layers and are weak; serves→applicationservice is the more defensible link.

### motivation

- **assessment**: Associated-with to outcome and constraint is inconsistent with influence to goal, requirement and principle; an assessment shaping an outcome or constraint would likewise be influence. Influence toward driver inverts ArchiMate's convention, where assessments are associated with drivers they evaluate. Assessment-to-assessment influence risks overlapping generic association.
- **constraint**: constrains and influence toward motivation.requirement overlap: both express a constraint shaping a requirement. Modelers will struggle to choose between them. Keep 'constrains' for limiting the solution space. Reserve 'influence' for weaker, non-restrictive effects, or drop that relationship.
- **driver**: The two associated-with links are weak: a driver-to-constraint link is usually causal and would be better expressed as influence, as with goals and requirements. Driver-to-value association is vague and may duplicate paths through goals or outcomes.
- **goal**: Goal aggregates requirement inverts usual ArchiMate direction (requirements realize goals). goal realizes goal overlaps with goal aggregates goal and influence goal as decomposition variants. influence and supports toward principle are largely redundant. Goal realizing value is unusual; association is more typical. Influence toward assessment reverses the normal assessment-influences-goal direction.
- **meaning**: All six use the generic associated-with, which is ArchiMate's only permitted relation for Meaning but carries little semantics; direction is ambiguous since Meaning interprets a concept rather than the motivation element itself. The meaning-to-stakeholder link is the most substantive (whose interpretation); others essentially say 'defines a term used in'.
- **outcome**: influence and realizes toward motivation.goal overlap; modelers should pick realizes for full attainment and influence for partial contribution. The associated-with links to constraint and driver are weak; constrained-by toward constraint and a driver→outcome influence would be more precise.
- **principle**: principle realizes goal overlaps with principle influence goal, and ArchiMate does not allow principles to realize goals (they realize nothing; goals are refined by principles via influence/realization from requirements). Consider removing realizes, or restricting it, to avoid two predicates expressing the same contribution.
- **requirement**: Requirement aggregates goal inverts the usual hierarchy; goals are refined by requirements, so this should likely be removed or reversed. Requirement associated-with goal overlaps with realizes goal; prefer realizes when the requirement actually refines the goal. Aggregates requirement and specializes requirement must be distinguished as decomposition versus variant.
- **stakeholder**: associated-with and influence to both driver and goal overlap; influence subsumes association when the stakeholder shapes the element, so the associated-with variants risk redundancy unless reserved for passive concern. Stakeholder associated-with constraint is weak; ArchiMate typically links stakeholders to drivers/goals, with constraints reached via requirements.
- **value**: Value-to-stakeholder is the only link ArchiMate expects here; the rest use generic associated-with, which hides meaning. Value-to-outcome would read better as outcome 'delivers' value. Value-to-goal would read better as 'supports'. Value-to-constraint is weak: constraints restrict the solution, not value. A self-association on value adds little unless it is meant as an aggregation.

- **stateaction**: flows-to from StateAction to StateTransition inverts the documented containment (transitions own and run actions); if the intent is an action dispatching an event that fires a transition, 'triggers' fits better. 'specializes' to StateActionTemplate really describes instantiation with parameter values, not subtyping; 'realizes' or 'implements' would be more accurate.
- **stateactiontemplate**: implements and provides both link the template to StateAction with the same meaning (the action instantiates the template); keep one. implements is also inverted, since the concrete StateAction realizes the abstract template, not the reverse. governs StateTransition is indirect, because the template only constrains transitions through the StateActions placed on them.
- **statepattern**: Aggregates and governs on the same pattern-to-state pair overlap: membership plus rule-setting may be acceptable, but governs is a motivation-layer influence predicate and fits poorly for UX structure. Consider composes if states are defined inline in the pattern. Also, TransitionTemplate names an animation, which risks confusion with state-machine transitions.
- **statetransition**: navigates-to is a questionable predicate here: it is catalogued as UI navigation between screens or routes, while ExperienceState is explicitly not a screen or route. A dedicated 'targets-state' predicate, or flows-to, would fit better. associated-with to ActionComponent is vague; 'triggered-by' would express the event-source role more precisely.
- **subview**: uses.ux.librarysubview duplicates realizes.ux.librarysubview, since both express the ref placement. Keep realizes. renders and aggregates of componentinstance overlap. Prefer composes for inline sub-views. uses.layoutconfig fits applies better. serves.applicationservice reverses the usual direction: the service serves the UI. accesses.collection skips the API layer.
- **tablecolumn**: The two maps-to relationships, to data-store.field and to data-model.schemaproperty, plus binds-to dataconfig all describe the column's data source; the column should usually map to the schema property only. Renders componentinstance is odd because the column is itself part of a table ComponentInstance. Uses layoutconfig overlaps with the column's own width and alignment attributes.
- **transitiontemplate**: A TransitionTemplate describes how a change animates, not which change occurs, so flows-to ExperienceState/SubView and navigates-to View misstate its role; applies (template applied to these elements) fits better and would be consistent across targets. triggers StateAction conflicts with StateAction being executed by state/transition lifecycle hooks, not animations. governs StateTransition also overlaps with applies.
- **uxlibrary**: Aggregates and provides overlap for both destinations: membership and export usually coincide. Keep 'aggregates' only if it carries internal and unexported members; otherwise drop one. Also note the UXLibrary description mentions state and action patterns, but no relationships cover them.
- **uxspec**: uxspec.governs.errorconfig is plausible only if specs define default error policies; otherwise error configs attach to views, components, routes and bindings, which makes this link indirect. Aggregating experience states alongside views is fine, but states are usually composed within a state machine and do not exist independently, so composes may fit better than aggregates.
- **view**: uses.layoutconfig duplicates applies.layoutconfig; keep applies. aggregates.subview and composes.subview overlap and need a ref-set versus inline distinction. renders.componentinstance overlaps with aggregates.actioncomponent. realizes.motivation.goal should be supports-goals. maps-to is a data-mapping predicate and is misused for outcome and businessobject. serves.applicationservice is inverted: services serve the UI.
