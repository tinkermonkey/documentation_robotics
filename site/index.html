Spec-driven development, down to the element

Documentation Robotics turns a codebase into a typed graph of the whole system: the goals it serves, the features and services that deliver them, the APIs, schemas, tables and screens that implement them, and the spans and tests that watch and prove them. You extract the graph from the code you already have, on top of the codebase-memory-mcp code graph, then refine it and explore it. Then you plan each change on it. The graph checks the plan before code is written, and checks the code against the plan once it is.

The idea

A spec at the grain of the code

Spec-driven development asks for the plan before the code. Most plans are prose written at the level of a feature: they say what to build and leave the reviewer to work out what it touches. DR keeps the spec at the level of each element and each connection, so a plan can be checked by walking the graph instead of by memory.

A prose specA DR spec
UnitA feature, in paragraphsEach goal, feature, service, endpoint, schema, table, screen, span and test as a typed element
LinksImplied by the wordingTyped, directed relationships the spec allows between those types
Checked byA reviewer's memoryThe graph: what a change reaches, misses and can break
LifetimeThe session or the ticketCommitted with the code, and kept true to what is built
Against the buildNot comparedCompared, by extracting the branch and diffing it with the plan

Built on a code graph

An opinionated reading of the code graph

codebase-memory-mcp parses a codebase into a graph: files, classes, functions and routes, joined by calls, imports, data flows and tests. That graph says how the code is wired, in each language's and framework's own terms. DR reads it with opinions. It projects every node and edge onto one of the 13 layers and a type the spec defines, so the same idea written in different stacks becomes the same element.

Tier 0ships

Rules

Mappings and framework conventions settle the common cases: 10 node mappings, 45 edge mappings and 27 rules in spec 0.12.0. Same code, same answer, every run.

Tier 1in progress

Decision model

Calibrated answers for what the rules can't settle: which layer, which type, how significant. Confident answers stage on their own; the rest go up a tier.

Tier 2ships

Claude

Names and describes elements, decides the cases left over, and adds the layers no code records: goals, requirements and features.

Shared concepts across stacks

A Spring controller, a FastAPI route and a Next.js page all become operations, functions and views. One question works on every repo.

Architecture grain, not symbol grain

Accessors, generated clients and fixtures are left out, so the model holds the elements a person would draw.

Runs you can compare

The same code reads the same way each time, so verify and drift compare like with like.

Get started

From install to a changeset in your pull request

Six steps along the path. Each is useful on its own and unlocks the next. After the first, you work by asking Claude.

  1. 01

    Install and set up

    once per machine

    Needs Node.js 18 or later and Claude Code. Extraction reads the code through codebase-memory-mcp.

    $ npm install -g @documentation-robotics/cli codebase-memory-mcp
    $ claude plugin marketplace add tinkermonkey/documentation_robotics
    $ claude plugin install dr@documentation-robotics
    > What's the DR status of this repo?
    UnlocksThe dr tools in every Claude Code session. project_status says where the repo stands and names the next step; for a new repo, Claude creates an empty model.
  2. 02

    Extract the as-built model

    once per repo

    Claude indexes the code, then stages what it finds as one changeset. Rules decide the common patterns, and the rest come back to Claude to decide. Nothing is written to the model yet.

    > Index this repo and extract a DR model from the code.
    UnlocksThe implementation layers drafted from source: services, functions, APIs, schemas, storage, screens, routes and tests, each with a reference to its file.
  3. 03

    Refine it, and add what code can't show

    once, then as needed

    Open the changeset in the viewer. Comment on what's wrong, and Claude fixes it or rejects code that isn't an element. Then add the layers no codebase records: the goals, requirements and features the code serves. You commit the changeset when it's right.

    > Open the extraction for review, then help me add the goals and features it serves.
    UnlocksA committed model that matches the code and traces it to intent. From here, project_status tells you when the code has moved on without the model.
  4. 04

    Explore it

    first value

    Ask questions the code can't answer quickly: why something exists, what depends on it, which endpoints have no tests or telemetry. Browse the graph in the viewer, or export it for the standards your team already reads.

    > Which API operations have no test sketch or span?
    $ dr export openapi
    UnlocksOnboarding, impact questions and coverage gaps answered from one map. ArchiMate, OpenAPI, JSON Schema, PlantUML, Mermaid and Markdown from the same source.
  5. 05

    Plan your next change as a changeset

    every change

    Claude opens a changeset with the intent, looks up what exists and what the spec allows, stages the change across layers, and pressure-tests it. It closes each gap or tells you why it accepts it, then opens the plan in the viewer for your comments.

    > /dr-plan let admins export orders as CSV
    UnlocksMissing tests, policies, telemetry and storage found before the code exists, and a plan reviewed on the graph instead of in paragraphs.
  6. 06

    Build, verify and land it in the PR

    where the value compounds

    Claude builds from the brief: the changes by layer, their connections, and the files of the existing elements they touch. It extracts the branch and compares it with the plan, and fixes the differences in the code or the changeset. You confirm the commit, and the changeset merges with the code.

    UnlocksA model on main that never claims what isn't built, and a record of how far each build strayed from its plan.
Why plan on the graph

The graph reviews the plan before any code is written

A prose plan lists what the session thought of. A changeset is projected across the graph, and the brief shows what it reaches, what it misses and what it can break.

Impact

Every existing element the change can break, by layer, with the source file it lives in.

Reach

Which layers the change touches. An API operation with nothing in testing or APM is either small or unfinished, and you see which.

Connections

Connections the spec allows, or that similar elements have, and the new element lacks.

Consistency

The model as the change leaves it still validates: schemas, references, relationship types.

Intent

Each change traces up to a goal, requirement or feature. One that traces to nothing becomes a question for you.

The value

What a team gets from a model it can trust

value

  • A map of what you already have

    The whole system in one graph, drawn from the code and linked back to it.

  • Traceability from code to goal

    Every endpoint, table and test traces to the feature and goal it serves, or you learn that it doesn't.

  • Gaps found before code

    The missing test, policy, span or table shows up in the brief, not in review or production.

  • Plans that outlive the session

    A changeset is a file on the branch, reviewed on the graph and merged with the code it describes.

  • Builds checked against plans

    Verify lists what was built but not planned, and planned but not built.

  • A person holds the commit

    Agents stage, project and explain. Nothing lands in the model until someone confirms it.

you'll know it's working when
  1. 01New people answer "why does this exist?" from the model, not from whoever wrote it.
  2. 02Changes are planned as changesets instead of prose plans.
  3. 03Pressure-testing finds things a prose plan would have missed, and you can name them.
  4. 04Each changeset is committed in the pull request that ships its code, and the difference between plan and build is small and explained.
Where it stands

What works today, and what's coming

Works todaycli 0.4.0
  • Extraction into a reviewable changeset, with rules for the common patterns and Claude for the rest.
  • Change modeling end to end, from plan to confirmed commit, all over MCP.
  • Live review in viewer 0.9.0: comments reach the agent as you make them.
  • Spec 0.12.0, with dr upgrade migrations for every breaking change.
In progressextraction
  • Faster, cheaper extraction. A decision model takes the calls the rules can't make, so fewer symbols go to Claude. Today most TypeScript symbols still do.
  • More relationships from code: inheritance, HTTP calls between services, and connections to databases and queues.
  • Finer review of an extraction: reject an extracted relationship, or a whole file or folder, and keep source references when a plan lands.
Plannednot started
  • Accepted gaps. Record a gap you accept, with the reason, so the brief stops raising it. #1026
  • Tests from TypeScript and JavaScript. Anonymous it() cases don't become testing elements yet.
  • Infrastructure from code: tables, container images, cloud resources and processes.
  • Many repos kept current from CI, with drift checks across a set of models.
  • Extraction that learns from the changesets you approve.
